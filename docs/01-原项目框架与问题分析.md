# 原项目框架与问题分析

> 本文只讨论改造前的开源起点及当时的审计结论。最终版本已经解决了其中一部分问题，具体变化请看[改造报告](02-从原项目到当前版本的改造报告.md)。

## 1. 为什么先分析原项目

我最初选择 [voyager-jhk/DeterministicMatchingEngine](https://github.com/voyager-jhk/DeterministicMatchingEngine)，是因为它的主题和量化开发实习比较贴近：C++、订单簿、撮合、对象池、延迟测试和回放都能在一个不算太大的项目里看到。

但“代码里出现了这些关键词”不等于项目已经达到真实交易系统的质量。审计时我把问题拆成三层：

1. **业务结果是否正确**：订单是否按价格和先后顺序成交，数量是否守恒；
2. **工程行为是否可靠**：非法输入、容量不足、回放和内存生命周期是否清楚；
3. **性能宣传是否成立**：测试口径能否代表完整路径，结果能否在声明环境复现。

这三个问题必须分开。一个撮合规则正确的教学项目，可能还没有可靠恢复；一个微基准很快的函数，也可能不包含事件、日志、网络和风控。

## 2. 原项目想解决什么问题

撮合引擎接收买卖订单，维护尚未成交的挂单，并在价格可以成交时决定：

- 谁先成交；
- 以什么价格成交；
- 成交多少；
- 哪些订单还留在订单簿；
- 撤单时应删除哪一笔订单。

基础限价撮合通常遵守：

- 买方价格越高越优先；
- 卖方价格越低越优先；
- 同一价格上先到的订单先成交；
- 成交价取原来挂在订单簿上的被动单价格。

原项目围绕这些规则搭建了一个单线程订单簿原型。

## 3. 原项目的主要框架

改造前可以简化成下面这条路径：

```text
新单 / 撤单
     │
     ▼
MatchingEngine / OrderBook
     │
     ├── 订单对象池：保存活跃订单
     ├── 订单 ID 索引：撤单时按 ID 查订单
     ├── 买方价格表：从最高买价开始
     ├── 卖方价格表：从最低卖价开始
     ├── 价格层 FIFO：同价订单按到达顺序排队
     └── Event：记录新单、撤单和成交结果
```

### 3.1 整数价格

原项目不直接用 `double` 当价格键，而是把价格放大后存成整数。这个方向值得保留，因为十进制价格用二进制浮点表示时可能出现边界误差。

例如：

```text
100.00 -> 1,000,000
100.01 -> 1,000,100
```

但是“使用整数”只解决表示问题，并没有自动解决 tick、价格范围和不同品种规则。放大倍数、最小变动单位和校验逻辑必须彼此一致。

### 3.2 订单对象池

对象池提前申请一批订单对象，运行时从池里取出和归还，避免每笔订单都单独 `new/delete`。它的价值是：

- 地址更稳定；
- 常见路径的内存分配更可预测；
- 能提前知道最大活跃订单数；
- 对低延迟研究比无上限动态增长更合适。

同时，对象池不是“无限容量”。池满时怎样拒绝、拒绝前是否已经写了事件、池中对象是否能安全复用，都需要额外验证。

### 3.3 每个价格一个 FIFO 队列

同价订单用双向链表排队，新单放在尾部，撮合从头部开始。这个结构直接表达同价先到先得：

```text
最早                                         最晚
Order 101 <-> Order 108 <-> Order 115 <-> Order 120
```

双向链表还允许在已经知道订单地址时 O(1) 摘除队中订单。但如果撤单先查到订单后，又按价格重新查一次价格层，就还有可以减少的重复工作。

### 3.4 有序价格容器

买方需要快速找到最高买价，卖方需要快速找到最低卖价。原项目使用有序容器维护价格层，这能让代码清楚且撮合结果正确，但树节点会带来：

- 新价格出现时可能动态分配；
- 空价格层消失时释放节点；
- 查找会跨多个不连续地址；
- 尾延迟受分配器和缓存未命中影响。

所以 `std::map` 并不是错误选择，它是教学和正确性阶段的合理选择；问题在于不能同时把它描述成所有热路径都已经零分配。

### 3.5 事件与回放

原项目有事件记录和 replay 的方向，这一点很有价值：确定性撮合不只要“这一次算对”，还要相同输入能重建相同结果。

但原模型把输入命令、执行结果和恢复含义混在一起。若从 `New/Cancel/Trade/Reject` 混合 Event 中反推哪些是输入，就会出现几个问题：

- Trade 是命令产生的结果，不应再次作为输入扣减数量；
- Reject 到底表示命令被消费，还是输入根本没有被接纳，不够清楚；
- 只比较最优买卖价会漏掉深层价格档和同价 FIFO 错误；
- 状态哈希若没有覆盖全部顺序字段，也不能作为唯一证据；
- 可读 CSV 往返不等于崩溃安全的持久化恢复。

## 4. 原项目值得保留的部分

这次改造不是推翻一切。原项目至少提供了四个很好的学习起点：

1. **价格—时间优先的核心撮合思路正确。**
2. **整数价格和强类型方向正确。**
3. **订单对象池和侵入式同价链表适合低延迟研究。**
4. **主动考虑事件和确定性回放，比只写一个成交函数更完整。**

真正的问题不是这些思路“完全错误”，而是工程边界、验证证据和宣传口径没有跟上。

## 5. 审计发现的主要差距

### 5.1 Windows / Visual Studio 可执行性不足

原项目更偏向 GCC/Linux，包含编译器相关的对齐、格式化和构建假设。对准备在 Visual Studio 学习的使用者来说，“仓库能下载”不等于“按 README 就能编译运行”。

一个简历项目首先要能被复现。否则后面的低延迟数字和架构说明都缺少基础。

### 5.2 输入规则不完整

订单簿不仅要处理正常订单，还要明确拒绝：

- 订单 ID 为 0 或重复；
- 价格小于等于 0；
- 数量为 0；
- 价格不在 tick 网格；
- 数量不在 lot 网格；
- 价格或数量超出品种限制；
- 订单池或索引容量耗尽；
- 撤单目标不存在。

如果调用方只得到一个模糊 `false`，回测很难区分策略问题、数据问题和系统容量问题。

### 5.3 订单 ID 索引仍可能扩容

通用 `unordered_map` 平均查找很快，但插入可能分配或 rehash。对普通业务这是方便的默认方案，对声称低延迟的热路径却需要更严格的容量和抖动控制。

### 5.4 价格层“池化”没有完全接入

只写一个池类并不等于主路径已经使用它。即使价格层对象本身池化，保存“价格到层指针”的 `std::map` 节点仍然可能动态分配。审计时必须沿着真实下单、成交、撤单路径检查，而不是只看类名。

### 5.5 撤单存在重复价格查找

如果订单 ID 索引已经返回订单地址，订单还可以直接保存所属价格层。否则撤单需要再用价格去有序容器找层，增加一次树查找。

### 5.6 同价顺序依赖“时间”但语义不够独立

现实系统有发送时间、网关接收时间、撮合接收时间等多种 timestamp。若核心 FIFO 使用一个含义模糊的 `current_time`，后续 replay、恢复和外部时间接入容易混在一起。

对确定性引擎，更直接的做法是使用只表达先后顺序的 `PrioritySequence`。

### 5.7 事件模型把输入和结果混在一起

“收到一条命令”和“订单簿发生一种状态变化”不是同一个概念。原模型里新单/撤单事件既像输入，又像输出；接受、挂单、成交和拒绝的关系不够清楚。

如果以后增加 Journal，这种混合会导致：系统到底保存 Command、保存 Event，还是从 Event 猜 Command？因此需要先把模型分开。

### 5.8 Replay 证据链不完整

只要两次 replay 的 BBO 一样，不能说明完整订单簿一样。下面两个账本可能最优价相同，但深度和 FIFO 不同：

```text
Book A: 100.00 -> Order 1(10), Order 2(20)
Book B: 100.00 -> Order 2(20), Order 1(10)
```

下一笔成交结果会不同。Replay 至少要比较事件字段、全部价格档、档内顺序、剩余数量、活跃订单数、BBO 和最后输入序列，并检查内部不变量。

### 5.9 缺少可学习的 Snapshot 边界

原项目的恢复说明容易把 CSV 回放说得过重，却没有一个清楚的“只保存业务状态、不保存内部指针”的内存 Snapshot。对学习架构来说，先实现内存 Snapshot 比直接进入磁盘日志更容易理解，也更容易测试。

### 5.10 内部结构缺少系统性审计

订单簿同时维护链表、价格层汇总、订单 ID 索引、对象池和最优价。只断言成交输出，可能漏掉内部半损坏，例如：

- 订单在链表里却不在 ID 索引；
- 层汇总数量不等于订单数量之和；
- 空层仍留在价格目录；
- 订单池已释放但链表仍引用；
- 同价顺序字段倒退；
- 买卖最优价已经交叉。

因此需要一个较重但完整的 `check_invariants()`，放在测试、恢复后审计和低频诊断中。

## 6. 如何看待原项目的“30 ns”宣传

纳秒数字不是完全没有意义，但必须先问测试包含什么。

### 6.1 一个微基准可能省略的内容

- 网络收包和协议解析；
- Command 构造和序列准入；
- 账户及仓位风控；
- EngineEvent 生成和发布；
- 磁盘 Journal；
- 跨线程队列和线程唤醒；
- 多档成交、价格层创建和撤单；
- 操作系统调度和尾延迟。

如果只测“预热后向已有同价层追加订单”，它当然可能远快于一笔真实订单的端到端处理。

### 6.2 平均值不能代替分布

下面几种表述差别很大：

- 最好的一次是 30 ns；
- 多轮中位数是 30 ns；
- P99 是 30 ns；
- 包含网络、风控和日志的端到端 P99 是 30 ns。

原项目宣传没有充分区分这些口径，因此不能直接把数字放进简历作为稳定能力。

### 6.3 计时器也会误导

几十纳秒已经接近单次高层计时接口的可见粒度。逐笔统计可能出现 `0 ns`，这只说明操作短于计时粒度，不代表没有成本。更可靠的方式是批量执行、预热、多进程重复，同时报告中位数和场景。

### 6.4 本项目最后得出的结论

后续优化确实让若干关闭事件的批量微基准进入 25–27 ns，但新价格层约 73 ns、扫四档约 186 ns。事实证明“30 ns”可以是某条窄路径的研究结果，不能当成整个引擎或真实交易链路的统一延迟。

详细数据和版本边界见[改造报告](02-从原项目到当前版本的改造报告.md)。

## 7. 审计结论汇总

| 原项目主张或结构 | 审计结论 | 需要怎样补齐 |
|---|---|---|
| 整数价格 | 方向正确 | 增加 tick、lot、范围和统一配置 |
| 订单对象池 | 有价值 | 明确容量失败、生命周期和复用安全 |
| 同价双向链表 | 适合 FIFO | 使用独立 PrioritySequence，并检查严格递增 |
| `unordered_map` 订单索引 | 功能正确 | 固定容量、避免 rehash、验证冲突删除 |
| 有序价格树 | 清楚且正确 | 诚实说明节点分配，用快速价格梯辅助 |
| 价格层池 | 不能只看类名 | 接入真实主路径，并承认 map 节点仍存在 |
| Event Replay | 思路有价值 | Command/Event 分离，重执行命令并完整比较 |
| 状态哈希 | 适合作为快速信号 | 不代替逐字段状态和 invariant |
| 30 ns | 只可能描述受限微基准 | 固定环境、场景、版本和聚合方法 |
| “可用于交易” | 作为学习原型可以 | 不能宣称具备生产网络、风控和恢复能力 |

## 8. 为什么这个项目仍然适合作为量化开发入门项目

审计发现问题，并不代表项目失去价值。相反，它比只写一个普通管理系统更能展示：

- 对交易规则的理解；
- 对 C++ 内存布局和容器行为的理解；
- 对确定性、顺序和恢复语义的理解；
- 用测试证明数据结构改动没有破坏业务；
- 对基准数据保持克制，不把局部数字夸成完整系统能力。

真正有价值的项目叙述不是“我复制了一个 30 ns 撮合引擎”，而是：

> 我从一个开源原型出发，复现并审计它，发现输入输出模型、容量边界、回放证据和性能口径存在差距；随后用明确的数据模型、固定容量结构、完整状态验证和可追溯基准逐步修正。

这也是后续改造的出发点。
