# 原项目框架与问题分析

> 本文记录我为什么选择这个项目、原项目是怎样工作的，以及我在真正编译、运行、测试和压测之后发现的问题。这里的目的不是否定原作者，而是把“一个有启发性的教学原型”和“一个可以认真写进量化开发简历的工程项目”区分开。

## 1. 我为什么从这个项目开始

我想找一个适合量化开发入门的 C++ 项目。相比普通的管理系统，订单簿和撮合引擎同时涉及金融交易规则、数据结构、内存管理、正确性验证和性能测试，比较适合作为我从 C++ 开发走向量化开发的切入点。

原项目最吸引我的地方有三点：

1. 它不是只计算一个策略收益，而是模拟了交易系统里真正会出现的“挂单、成交、撤单”。
2. 它已经有订单池、价格层、事件日志和回放这些基本概念，方向是对的。
3. 它提出了“确定性”和“低延迟”两个目标，能够让我继续追问：同样的输入是否一定得到同样的结果？性能数字到底是怎么测出来的？

所以我没有把它当成一份可以直接使用的成熟代码，而是把它当成一个需要审计和重构的起点。

## 2. 原项目想解决什么问题

限价订单可以简单理解为：

- 买方说：“价格不高于 10.00 元时，我愿意买 100 股。”
- 卖方说：“价格不低于 10.00 元时，我愿意卖 100 股。”

撮合引擎需要接收这些订单，按交易规则决定它们是立即成交，还是留在订单簿里等待。常见规则是“价格优先、同价时间优先”：

- 买单里出价更高的先成交；
- 卖单里报价更低的先成交；
- 价格相同时，先到的订单先成交。

原项目希望在一台普通计算机上实现一个简化版本，并进一步做到：

- 处理速度快；
- 同一批输入可重复回放；
- 尽量少在撮合过程中临时申请内存；
- 能记录接受、成交和撤单等事件。

这些目标本身很适合作为工程项目，但目标是否实现，必须通过代码路径、异常情况和可重复测试来证明，不能只看 README 里的数字。

## 3. 原项目的总体框架

原项目的核心流程可以简化成下面这样：

```text
外部订单
   │
   ▼
MatchingEngine（撮合入口）
   │
   ├── 买卖价格是否能够成交？── 是 ──► 逐笔撮合并生成成交事件
   │
   └── 否 / 还有剩余数量 ─────────► 放入订单簿
                                      │
                                      ├── std::map 保存价格层
                                      ├── 每个价格层保存同价订单队列
                                      └── unordered_map 按订单号查找订单
```

主要模块及作用如下：

| 模块 | 原项目中的作用 | 通俗理解 |
|---|---|---|
| `MatchingEngine` | 接收新订单和撤单，执行撮合 | 总调度员 |
| `OrderBook` | 分别维护买方和卖方订单 | 当前市场上还没成交的订单集合 |
| `bids_` / `asks_` 价格表 | 用两个 `std::map` 排序买卖价格 | 两排按价格排序的抽屉 |
| `LimitLevel` | 保存同一个价格上的订单 | 某一个价格抽屉里的排队队伍 |
| `OrderPool` | 预先准备订单对象，循环使用 | 提前准备好的一批空表格 |
| 订单号索引 | 通过订单号找到订单 | 撤单时使用的通讯录 |
| `EventLog` | 保存接受、成交、撤销等事件 | 系统流水账 |
| `ReplayEngine` | 读取记录并再次执行 | 把历史操作重新演一遍 |

## 4. 原项目一次下单是怎样完成的

### 4.1 新订单进入系统

原项目收到新订单后，大致会做这些事：

1. 从对象池取出一个订单对象；
2. 根据买卖方向查找对手方最优价格；
3. 如果价格能够成交，就从最优价格层的第一笔订单开始撮合；
4. 如果新订单没有完全成交，就把剩余部分加入自己的买方或卖方订单簿；
5. 把订单号和订单地址放进索引，方便以后撤单；
6. 生成相关事件。

### 4.2 同价订单如何排队

同一个价格上可能有很多订单。原项目没有给每个订单再分配一个独立容器节点，而是让订单对象本身保存前后指针，组成双向链表。

```text
价格 10.00：订单 A ⇄ 订单 B ⇄ 订单 C
```

这样做的思路是合理的：

- 新订单放到队尾比较快；
- 成交时从队头取最早的订单；
- 已知订单地址后，理论上可以较快地把它从队伍中摘掉。

### 4.3 价格如何排序

原项目使用 `std::map` 保存价格层。它能够自动保持价格有序，因此容易找到最低卖价和最高买价，也容易实现价格优先规则。

这个选择的优点是正确、清晰、通用；缺点是每创建一个新价格层，`std::map` 自己仍然要申请树节点，而且查找会经过多个分散的内存地址。它适合先把功能做对，但不是追求极端低延迟时最理想的最终结构。

### 4.4 撤单如何完成

撤单不能从所有价格和所有订单中逐个查找，否则订单一多就会很慢。原项目额外维护了一个 `unordered_map`，用订单号找到订单对象，再根据订单价格找到对应价格层，最后删除订单。

基本方向没有问题，但 `unordered_map` 的扩容、散列冲突和动态内存分配会让某些请求突然变慢。平均时间快，不代表每一次都稳定。

### 4.5 回放如何完成

原项目尝试把事件保存下来，再通过回放模块重新执行。这个设计想表达的是：如果输入顺序完全相同，那么最终订单簿也应该相同。

确定性对量化回测很重要，因为策略结果如果每次运行都不同，就难以排查究竟是策略变化、数据变化，还是程序自身存在不稳定行为。

## 5. 原项目值得保留的部分

经过审查，我认为以下思路是有价值的，也成为后续改造的基础：

- 使用整数价格，避免直接用浮点数比较金融价格；
- 每个价格层按到达先后保存订单；
- 订单对象使用侵入式链表，减少额外节点；
- 使用对象池复用订单内存；
- 用事件描述系统发生了什么；
- 希望用状态哈希检查回放结果；
- 把核心结构写成模板，便于调整容量。

因此后续改造不是全部推倒重写，而是保留正确的方向，把没有落地的部分补实，把夸大的部分改成可验证的说法。

## 6. 我怎样审查原项目

我没有只看代码是否“看起来很快”，而是按下面的顺序检查：

1. 在 Windows + Visual Studio/MSVC 环境实际编译；
2. 运行演示程序，观察接受、成交、撤单顺序；
3. 构造非法价格、非法数量、重复订单号、订单池耗尽等情况；
4. 构造跨多个价格层成交、部分成交和撤销中间订单；
5. 检查订单簿内部数量、链表、索引是否一致；
6. 执行事件回放，并比较回放后的完整状态；
7. 反复创建和删除价格层，观察内存和耗时；
8. 将只测核心函数的延迟与完整业务路径的延迟分开；
9. 使用 AddressSanitizer 等工具检查越界、释放后使用和重复释放；
10. 对 README 中的性能、内存占用和功能描述逐项找证据。

## 7. 原项目存在的主要问题

### 7.1 README 的宣传数字缺少足够证据

原项目宣传过接近 `30 ns`、每秒数千万订单、订单对象只有几十字节等亮眼结果。问题不在于数字一定完全不可能，而在于：

- 没有清楚说明测的是哪一段代码；
- 没说明是否包含事件记录、索引更新和价格层创建；
- 没给出稳定的测试环境、编译器参数和多轮分布；
- 单次或平均值不能说明尾部延迟；
- 对象本身大小不等于一笔订单在整个系统中的真实内存成本。

例如，一笔订单除了订单对象，还会占用订单号索引槽位、价格层、树节点、事件和容器空余容量。只报告 `sizeof(Order)` 会低估系统总内存。

我的结论是：这些数字可以看成优化目标或特定微基准结果，不能直接当成完整撮合引擎在真实业务路径上的稳定能力。

为了避免只做模糊评价，我把重构前 README 中最关键的声明和实际代码证据整理如下：

| 原 README 的声明 | 我核查后的判断 | 没有达到完整含义的原因 |
|---|---|---|
| 混合吞吐约 1640 万操作/秒 | 可能是特定 WSL2 基准结果，但无法代表所有混合业务 | “50% Add / 50% Cancel/Trade”的订单分布、活跃数量和事件口径说明不足 |
| 纯挂单约 5000 万操作/秒 | 只能理解为非常短且高度预热的批量路径 | 5000 万/秒约等于 20 ns/操作，与同页 30 ns 中位数口径也需要进一步解释 |
| P50 约 30 ns | 有微基准探索价值，不能视为完整路径 | 没有包含网络、协议、风控和持久化；容器扩容与新价格层也未必进入样本 |
| P99 约 800 ns | 能说明作者意识到尾延迟，但复现实验信息不够 | 缺少原始样本、轮数、线程绑定、CPU 型号和明确操作混合 |
| 撤单约 15 ns | 链表摘除本身很短，但完整撤单还需要订单号查询、索引删除和空层处理 | “O(1) 链表操作”和“完整撤单延迟”不能直接画等号 |
| 裸机隔离后 P99 预计低于 200 ns | 这是预期，不是现有实验结果 | 没有裸机测试数据就不能写成已经证明的能力 |
| 热路径零分配 | 与实际容器使用存在冲突 | 订单池能避免订单 `new`，但 `unordered_map`、`std::map` 和事件容器仍可能分配 |
| 订单正好占一个 64 字节缓存行 | 即使对象大小满足，也不等于一笔订单全部成本只有 64 字节 | 索引、价格层、map 节点和事件是额外内存；缓存命中也不只由对齐决定 |
| 可以 bit-exact / exact replay | 回放方向正确，但原有验证闭环不够完整 | 磁盘解析、拒绝结果、逻辑时间和完整队列状态没有全部形成严格证据链 |

这里最重要的不是证明原数字“造假”，而是区分三件事：作者机器上的一次测试结果、特定代码片段的微基准、整个可恢复撮合系统的稳定能力。原 README 把这三层放得太近，容易让学习者误解。

### 7.2 “30 ns”与完整撮合路径不是一回事

30 纳秒非常短。在普通桌面 CPU 上，它只相当于几十到一百多个时钟周期。完整下单却可能需要：

- 检查参数；
- 查询订单号；
- 查找对手价格；
- 修改链表和剩余数量；
- 更新索引；
- 生成多个事件；
- 必要时创建价格层；
- 处理分支和缓存未命中。

如果只测一个已经预热、没有成交、没有事件、没有新价格层的最短路径，接近几十纳秒是有探索空间的；如果把解析网络报文、风控、持久化和完整统计都算进去，就不能再把这个数字混为一谈。

### 7.3 Windows / Visual Studio 下不能直接稳定构建

原项目更偏向 GCC/Linux 写法，一些对齐属性、格式化接口和编译参数在 MSVC 下并不完全兼容。这意味着对于主要使用 Visual Studio 的学习者，README 所描述的“开箱即用”并没有真正成立。

构建问题看起来不是业务问题，但一个项目如果不能在声明的平台稳定编译，就无法继续测试正确性和性能。

### 7.4 订单号索引会在运行时产生不可控抖动

原实现使用 `unordered_map` 保存订单号到订单地址的映射。它的平均查找速度不错，但有几个低延迟系统不喜欢的特点：

- 插入时可能临时申请内存；
- 容量不足时会整体扩容；
- 冲突较多时查找次数上升；
- 删除后容器内部状态不容易精确预测。

这不一定导致功能错误，却会让“多数请求很快、偶尔一笔突然很慢”。真实低延迟系统不仅关心平均数，也关心 P99、P99.9 这样的慢请求尾部。

### 7.5 价格层虽然有对象池，`std::map` 节点仍会分配

原项目强调了对象池，但对象池主要覆盖订单。价格层以及 `std::map` 内部树节点仍可能在运行时创建和销毁。

这说明“撮合热路径零分配”并未完整实现。即使后来给价格层本身加池化，只要外层仍是 `std::map<价格, 价格层指针>`，树节点分配和指针跳转问题仍然存在。这个问题不能靠一句“已池化”掩盖。

### 7.6 撤单路径存在重复查找和不必要工作

原项目已能通过订单号找到订单，但订单没有直接记录自己属于哪个价格层。撤单时还要根据价格再次从价格表中查层。

这相当于已经找到了排队的人，却还要再查一次他站在哪条队伍。订单量大、价格层多时，这部分工作会影响撤单延迟，也使删除逻辑更复杂。

### 7.7 输入校验和拒绝原因不够完整

真实系统不能默认所有调用者都传入正确数据。原项目对下列情况覆盖不足或表达不清：

- 订单号为零；
- 买卖方向非法；
- 价格或数量为零；
- 价格不符合最小变动单位；
- 数量不符合最小交易单位；
- 订单号重复；
- 单笔数量超过限制；
- 订单池耗尽或标准容器分配失败；
- 价格和数量相乘发生整数溢出。

如果只返回 `false`，调用方不知道是参数错、容量满，还是系统内部故障，也无法在回测报告里统计不同拒绝原因。

### 7.8 失败操作可能留下不完整事件

接受订单、从池中分配对象、加入索引和写入事件之间必须有明确顺序。如果系统先写“订单已接受”，之后才发现订单池已满或索引插入失败，事件日志就会声称一笔实际没有进入系统的订单已经成功。

这种问题在演示时不容易发现，但回放时会产生逻辑矛盾。一个操作要么完整成功，要么明确失败，不能只完成一半。

### 7.9 事件回放没有形成完整闭环

原项目已经有回放概念，但早期版本主要覆盖新单和撤单，成交、拒绝、逻辑时间、配置和落盘解析没有全部进入一致性验证。

只比较少量字段也不够。例如最终买卖数量碰巧相同，不代表订单先后顺序、订单号索引和系统时间都相同。因此，“支持回放”与“可以证明确定性回放”之间还有明显距离。

### 7.10 事件容器会增长并触发重新分配

如果事件日志底层使用普通动态数组，事件不断增加时就会扩容并搬迁已有内容。对普通业务程序影响不大，但如果事件生成就在撮合热路径里，某一笔订单可能碰到扩容，延迟突然上升。

原项目没有把“记录完整事件的业务路径”和“关闭事件后的纯核心路径”分开报告，容易让性能结论含糊。

### 7.11 交易品种规则过于简化

原项目使用固定精度的价格整数，但没有把不同品种的规则系统化。真实市场里，不同股票、期货或数字资产可能有不同的：

- 最小价格变动；
- 最小下单数量；
- 最大价格；
- 最大单笔数量；
- 价格和数量缩放方式。

如果这些规则只藏在常量里，换一个品种就可能产生错误。尤其是原始默认 tick 与示例价格精度曾出现语义不一致，说明“整数价格”并不自动等于“价格规则正确”。

### 7.12 测试更偏演示，缺少内部一致性证明

只验证“程序没有崩溃”和“最后有一笔成交”远远不够。订单簿内部同时维护价格树、订单链表、订单号索引、对象池和汇总数量，任何一个漏更新都可能暂时不崩溃，却在后续撤单或回放时出错。

原项目缺少对这些内部关系的系统检查，也缺少长时间随机操作和极端容量测试。

### 7.13 基准测试场景不能代表所有实际场景

最短路径微基准通常会：

- 重复相似价格；
- 让数据全部留在 CPU 缓存；
- 避开字符串解析、磁盘和网络；
- 避免价格层频繁创建销毁；
- 只报告中位数或平均值。

它适合比较一次优化前后是否更快，但不能直接回答系统在行情高峰、撤单风暴、跨多档成交或日志落盘时的表现。原项目没有充分区分这些测试目的。

## 8. 为什么原项目没有达到宣传预期

综合代码和测试，我认为不是某一个函数写得不够快，而是目标定义、数据结构和验证方法之间没有完全对齐。

| 目标 | 实际阻碍 |
|---|---|
| 热路径稳定低延迟 | `unordered_map` 和 `std::map` 仍可能分配及产生缓存未命中 |
| 完整路径接近 30 ns | 校验、索引、价格查找、事件和成交更新共同消耗时间 |
| 确定性回放 | 输入格式、配置、逻辑时间和完整状态没有全部纳入闭环 |
| 可直接使用 | 平台兼容、错误处理、容量耗尽和交易规则不够完整 |
| 内存可预测 | 只池化部分对象，容器节点和事件容量仍可能增长 |
| 真实性能结论 | 测试环境、统计口径和尾延迟披露不足 |

因此，原项目更准确的定位是：一个展示订单簿、对象池和事件回放思路的教学原型。它给出了不错的起点，但还不是可以凭 README 数字直接当成交易基础设施的成品。

## 9. 我的总体判断
