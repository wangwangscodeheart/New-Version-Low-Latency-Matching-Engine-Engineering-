# 从原项目到当前版本的改造报告

> 这份文档记录主要改造留痕。每一部分都说明：原来有什么问题、做了什么、为什么这样选、解决了什么、还留下什么边界。

## 1. 改造目标

我的目标不是复制一个“30 ns”宣传页，也不是一次性造完整交易所，而是把教学原型整理成一个适合学习和继续开发的撮合引擎框架：

- 能在声明环境编译和运行；
- 撮合、撤单和拒绝语义清楚；
- 输入 Command 与输出 EngineEvent 分开；
- 顺序不依赖含义模糊的时间字段；
- Replay 能验证完整结果，而不是只看最优价；
- Snapshot 能在内存中重建全新引擎；
- 数据结构改动有单测、随机测试、invariant 和 ASan 保护；
- 性能结果能追溯到场景、环境和提交。

改造始终遵守三条顺序：先正确，再可验证，最后才谈局部性能。

## 3. 第一阶段：让项目在 Visual Studio 中可执行

### 原来的不足

原代码更偏向 GCC/Linux，对齐写法、格式化和编译选项在 MSVC 下不完全兼容。对 Windows 学习者来说，README 中的构建预期与实际环境存在差距。

### 修改内容

- 增加 CMake 的 MSVC 分支；
- 修正编译器相关的对齐和格式化写法；
- 统一 Demo、Unit、Property、Snapshot、Benchmark 的构建入口；
- 保留 GCC/Clang 和 Linux/WSL 构建方式；
- 增加 MSVC AddressSanitizer 配置。

### 结果和边界

Visual Studio 2022、x64 Release 可以直接构建，CTest 统一执行验证目标。跨平台能编译不代表跨平台延迟相同；性能数字仍必须绑定编译器、CPU 和系统环境。

## 4. 第二阶段：把品种规则和拒绝原因说清楚

### 原来的不足

原项目对非法价格、非法数量、tick、lot、重复 ID 和容量不足的处理不够统一。调用者可能只得到失败，却不知道失败来自策略、数据还是系统容量。

### 修改内容

新增 `InstrumentConfig`，集中管理：

- `tick_size`；
- `lot_size`；
- `min_price` / `max_price`；
- `max_order_quantity`。

补齐业务拒绝原因：

- `DUPLICATE_ORDER_ID`；
- `INVALID_PRICE`；
- `INVALID_QUANTITY`；
- `POOL_EXHAUSTED`；
- `INDEX_EXHAUSTED`；
- `ORDER_NOT_FOUND`；
- `PRICE_OUT_OF_RANGE`；
- `OFF_TICK_PRICE`；
- `QUANTITY_LIMIT`；
- `INVALID_LOT_SIZE`。

### 结果和边界

回测可以按原因统计拒单，测试可以精确断言失败。当前只检查撮合核心的品种规则，没有账户资金、持仓、交易时段、涨跌停和监管风控。

## 5. 第三阶段：替换热路径订单 ID 索引

### 原来的不足

`unordered_map` 平均查找很快，但插入可能分配和 rehash；删除若依赖墓碑，长期撤单后探测链可能恶化。

### 修改内容

实现 `FixedOrderIndex`：

- 启动时准备固定数量槽位；
- 开放寻址查找；
- `prepare_insert()` 只探测一次并返回预留位置；
- `commit_insert()` 在已确认位置提交，避免重复探测；
- 删除采用 backward-shift repair；
- 槽位压缩到 16 字节；
- 增加构造碰撞键、删除中间键并继续查找尾键的回归测试。

对应性能留痕：

- `559554f`：单次索引探测；
- `1f813e3`：压缩索引槽；
- `4e6a5ee`：冲突后移删除回归测试。

### 结果和边界

热路径不再因为订单 ID 索引扩容。代价是容量必须启动前规划，装载率过高时仍会增加探测次数，因此固定容量不等于固定一步访问。

## 6. 第四阶段：订单和价格层真正池化

### 原来的不足

订单对象虽然有池，但初始化仍可能产生不必要的临时对象复制；价格层池如果没有接入真实挂单、成交和撤单路径，对主路径没有帮助。

### 修改内容

- 订单对象在池内原地激活，减少临时构造和复制；
- 建立买卖双方共享的 `LimitLevelPool`；
- 新价格出现时从层池取得对象；
- 最后一笔订单离开价格层后归还对象；
- 检查重复释放、错误归属、池耗尽和移动后的 owner 绑定；
- 将价格层池接入主撮合路径，而不是保留为孤立示例。

订单原地激活对应性能提交 `e4d59e2`。

### 结果和边界

订单和 `LimitLevel` 对象生命周期更可预测，层容量也能计算。但外层 `std::map<Price, LimitLevel*>` 的树节点仍可能动态分配。因此“价格层对象池化”不能宣传成“价格路径完全零分配”。

## 7. 第五阶段：撤单直达和价格访问分层

### 原来的不足

按订单 ID 找到订单后，再按价格查一次价格层是重复工作；每次同价访问都进入通用有序容器，也会增加成本。

### 修改内容

- `Order` 保存 `parent_level` 指针；
- 撤单由“ID 索引 -> 订单 -> 再查价格层”改成“ID 索引 -> 订单 -> 直接摘链”；
- `PriceLevelStore` 继续维护完整有序目录；
- `PriceLadder` 对配置范围内的已知价格做数组定位；
- 缓存最近使用的买方和卖方价格层；
- 空层删除时同步层池、价格梯、目录和缓存。

### 结果和边界

撤单已知订单后可以 O(1) 从同价链表摘除，常见同价访问减少树查找。最优价排序和范围外价格仍由 `std::map` 保证正确，因此新建/删除价格档仍可能出现树节点成本。

## 8. 第六阶段：建立内部正确性安全网

### 原来的不足

只看成交结果不能发现所有内部损坏。链表、价格层汇总、ID 索引、订单池、层池、价格梯和缓存指针可能出现局部不一致。

### 修改内容

实现 `check_invariants()`，检查：

- 最优买价严格低于最优卖价；
- 不存在空价格层；
- 订单前后指针、头尾和层归属一致；
- 同价 `PrioritySequence` 严格递增；
- 层汇总数量等于订单剩余量之和；
- 链表订单和 ID 索引互相可达；
- 活跃订单数与订单池使用量一致；
- 活跃价格层数与层池使用量一致；
- 稠密价格梯和缓存指针指向真实价格层；
- 数量累加没有溢出。

### 结果和边界

这个函数是测试、Replay、Snapshot 恢复和低频审计的安全网。它需要遍历订单簿，不能放进每笔生产热路径。

## 9. 第七阶段：重新定义性能测试口径

### 原来的不足

一个平均纳秒数字把不同路径混在一起，很容易夸大。向已有同价层追加、创建新价格层、立即成交和跨四档成交不是同一件事。

### 修改内容

把微基准拆成：

1. `same_price_existing_level`；
2. `multiple_existing_levels`；
3. `new_price_level`；
4. `immediate_match`；
5. `four_level_sweep`。

性能阶段使用 5 个全新进程，每个进程 7 次，先取进程中位数，再取 5 个中位数的中位数。环境和数据写入：

- `benchmarks/results/2026-07-19-hotpath-optimization-summary.csv`；
- `benchmarks/results/2026-07-19-hotpath-validation.json`；
- 各优化阶段原始 CSV；
- `2026-07-19-rejected-experiments-summary.csv`。

### 性能阶段结果

环境：Intel Core i7-14650HX、MSVC 19.44、x64 Release、Balanced、未绑核、关闭事件记录。

| 场景 | 优化前 `3ba27a4` | 优化后 `e4d59e2` | 变化 |
|---|---:|---:|---:|
| 同价已有层 | 44.559 ns | 26.663 ns | 约 -40.2% |
| 多个已有层 | 43.876 ns | 27.104 ns | 约 -38.2% |
| 新价格层 | 79.730 ns | 73.090 ns | 约 -8.3% |
| 立即成交 | 43.838 ns | 24.988 ns | 约 -43.0% |
| 扫四档 | 200.090 ns | 186.440 ns | 约 -6.8% |

### 正确结论

30 ns 在三个窄微基准中可以接近或突破，但新建价格层和多档成交明显更慢。它不是完整撮合引擎的稳定延迟，更不是端到端实盘延迟。

架构 Sprint 后没有在最终提交 `9e43b8e` 上重新执行同口径矩阵，所以不能把上表标成“最终架构 HEAD 新测数据”。

## 10. 第八阶段：记录并回退失败的性能实验

改造过程中没有把所有尝试都保留。`2026-07-19-rejected-experiments-summary.csv` 记录了：

- 扩大公共价格梯分支：热点代码膨胀，同价常见路径退化；
- 缩小默认价格梯的额外分支：没有稳定全局收益；
- 强制 `Order` 64 字节对齐：主要路径退化；
- 自然 64 字节布局：部分场景变快，但同价主路径退化。

保留失败记录的原因是：低延迟优化很依赖数据分布和缓存布局。一个方案在某个场景变快，不代表总体更好；收益不稳定且增加复杂度时，回退比硬留更合理。

## 11. 第九阶段：Command 与 EngineEvent 分离

### 原来的不足

原 Event 同时承担输入命令、接受记录和执行结果，Replay 需要从混合 Event 猜哪些内容应该重新执行。

### 修改内容

提交 `7732018` 增加：

```cpp
using Command = std::variant<NewOrderCommand, CancelOrderCommand>;

using EngineEvent = std::variant<
    TradeEvent,
    OrderRestedEvent,
    OrderCancelledEvent,
    OrderRejectedEvent>;
```

统一入口：

```cpp
ProcessResult process(const Command& command);
```

旧的 `process_new_order()` / `process_cancel()` 暂时作为兼容包装，但内部仍然进入 `process()`。

### 为什么没有 `OrderAcceptedEvent`

本轮只记录实际结果：成交、挂单、撤销或业务拒绝。

- 全部主动成交的新单由一个或多个 `TradeEvent` 表达；
- 有剩余进入订单簿由 `OrderRestedEvent` 表达；
- 没有额外状态需要 `OrderAcceptedEvent` 才能表示。

少一个冗余事件还避免了“接受了但之后资源失败”的半语义。

## 12. 第十阶段：三个 Sequence 取代模糊时间语义

提交 `a4284a7` 明确：

- `CommandSequence`：输入命令的逻辑顺序；
- `EventIndex`：同一命令内事件的局部顺序；
- `PrioritySequence`：挂单在同价 FIFO 中的优先级。

规则如下：

1. `CommandSequence > 0`；
2. 新命令必须严格大于 `last_applied_command_sequence`；
3. 允许跳号；
4. 为 0、重复或倒退时直接准入拒绝；
5. 通过 gate 后即使命令业务拒绝，也推进最后序列；
6. 同一命令的事件索引从 0 连续递增；
7. 同价 FIFO 按 `PrioritySequence` 严格递增；
8. `Timestamp` 类型为了兼容仍留在 `types.hpp`，但不再参与核心撮合顺序。

### 结果

外部真实时间可以以后在适配层或审计模型中单独处理，不再与撮合先后顺序绑定。相同 Command 序列能稳定产生相同 FIFO 和事件索引。

## 13. 第十一阶段：把 Replay 改成 Command 重执行验证

### 原来的不足

旧回放从混合 Event 推断输入，主要比较 BBO 或哈希，无法严格证明深度、FIFO 和事件完全一致。

### 修改内容

提交 `c9bc03d` 实现：

```text
明确的 vector<Command>
        │
        ▼
全新 OrderBook 逐条 process
        │
        ├── EngineEvent 逐字段比较
        ├── OrderBookState 完整比较
        ├── 原始/重放引擎 check_invariants()
        └── state_hash 辅助比较
```

`OrderBookState` 包含：

- `last_applied_command_sequence`；
- 全部买方和卖方价格档；
- 每档总量；
- 每档 FIFO 中每笔订单的 ID、方向、价格、原始量、剩余量和优先序列；
- `active_order_count`；
- `best_bid` / `best_ask`。

收尾提交 `9e43b8e` 又把 invariant 检查放进 Replay 验证接口自身，而不是要求测试调用者在外面记得检查。失败时能够区分原始引擎、重放引擎或两者 invariant 失败。

### 保留的 CSV 到底是什么

`save_log/load_log` 仍可把 `EngineEvent` 保存成可读 CSV 并严格读回，用于诊断和字段往返测试。但它：

- 不是 Replay 输入；
- 不会从 Event 恢复订单簿；
- 不是 CommandJournal；
- 不是崩溃安全日志。

## 14. 第十二阶段：轻量内存 Snapshot

提交 `6068bfd` 实现 `OrderBookSnapshot`，保存：

- `snapshot_version`；
- `last_applied_command_sequence`；
- `InstrumentConfig`；
- `PriceLadderConfig`；
- 每笔活跃订单的 ID、方向、价格、原始量、剩余量和 `PrioritySequence`。

Snapshot 不保存内部指针、链表指针、对象池地址或 map 迭代器。

恢复流程：

```text
Snapshot
   │
   ├── 版本 / 配置 / 容量校验
   ├── ID / Side / Price / Quantity 校验
   ├── PrioritySequence 与重复校验
   ├── 分档数量溢出和 crossed book 校验
   ▼
按 Side、Price、PrioritySequence 排序
   ▼
构造全新 OrderBook
   ▼
重建订单池、ID 索引、价格层、FIFO、价格梯和 BBO
   ▼
恢复 last sequence + check_invariants()
```

失败返回 `SnapshotRestoreError` 和空指针，不把半恢复引擎暴露给调用者。

### Snapshot 的边界

- 只在内存中使用；
- 没有二进制格式、校验和或原子落盘；
- 不保存历史事件；
- 恢复后的事件容器从空开始；
- 只能比较恢复后的后续事件与未中断引擎的后缀；
- `snapshot_version` 目前只有简单版本 1，没有复杂兼容系统。

## 15. 第十三阶段：分开准入拒绝和业务拒绝

收尾审计重点检查 sequence gate 失败是否应该生成 `OrderRejectedEvent`。

最终采用：

| 情况 | ProcessStatus | EngineEvent | 推进 last sequence | 修改订单簿 |
|---|---|---|---|---|
| sequence 为 0、重复、倒退 | `SEQUENCE_REJECTED` | 无 | 否 | 否 |
| 通过 gate，但业务字段非法 | `REJECTED` | `OrderRejectedEvent` | 是 | 不改变有效挂单状态 |
| 正常执行 | `APPLIED` | 0 到多个结果事件 | 是 | 按命令结果修改 |

### 选择理由

Sequence gate 表示输入没有被引擎接受。若“命令未被接受”却产生一个 EngineEvent，将来增加 ExecutionJournal 时会出现输入记录和执行结果不对称。调用者已经可以从 `ProcessResult::status` 得到充分信息，所以不需要再增加 `AdmissionEvent`。

Replay 仍会接收包含重复/倒退序列的 Command 测试输入，但这些命令不会污染事件序列，两次执行仍应逐字段一致。

## 17. 改造前后集中对比

| 方面 | 原项目 | 当前版本 |
|---|---|---|
| Windows 构建 | 偏 GCC/Linux | VS2022、CMake、MSVC 可运行 |
| 输入模型 | 新单/撤单与 Event 边界混合 | 明确 `Command` variant |
| 输出模型 | 接受/撤单/结果概念交叉 | 四种 `EngineEvent` 只表达执行结果 |
| 统一入口 | 多个业务入口 | `process(const Command&)`，旧接口只做包装 |
| 命令顺序 | 模糊逻辑时间 | `CommandSequence` 严格 gate |
| 同命令事件顺序 | 隐含 | `EventIndex` 从 0 连续递增 |
| 同价 FIFO | 依赖到达时间含义 | 独立 `PrioritySequence` |
| 订单 ID 索引 | `unordered_map` | 固定容量开放寻址 + 后移删除 |
| 撤单找层 | 可能重复按价格查找 | 订单直连所属层，O(1) 摘链 |
| 价格层 | 生命周期不完整 | 主路径使用共享层池 |
| 价格目录 | `std::map` | 仍保留，并由 PriceLadder 加速常用已知价 |
| Replay 输入 | 从混合 Event 推测 | 明确 `vector<Command>` |
| Replay 比较 | 覆盖有限 | Event 全字段 + 完整 BookState + invariant + hash |
| Snapshot | 无清楚内存模型 | 版本 1 轻量内存 Snapshot |
| 准入拒绝 | 可能与业务拒绝混用 | `SEQUENCE_REJECTED` 无 EngineEvent |
| 性能报告 | 单点数字容易误读 | 多场景、多进程中位数、原始数据和失败实验 |

## 18. 当前仍未解决的问题

- `std::map` 节点仍可能在价格档出现/消失时分配；
- 事件 `vector` 超过预留后仍可能扩容；
- 未处理所有系统分配异常下的事务式回滚；
- Snapshot 不是磁盘恢复；
- 没有 CommandJournal、ExecutionJournal 或 Event Application；
- 没有参考引擎、差分测试和大规模故障注入；
- 只有基础限价单和撤单；
- 没有账户、持仓、交易时段、网络和多品种部署；
- 性能阶段结果没有在最终架构 HEAD 重新跑完整矩阵。

这些内容不是隐藏缺陷，而是当前版本的明确边界。后续方案见[当前项目的后续改进路线](03-当前项目的后续改进路线.md)。
