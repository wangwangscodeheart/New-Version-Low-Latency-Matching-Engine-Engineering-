# 从原项目到当前版本的改造报告

> 这份文档按实际改造顺序说明我做了什么。每一部分都回答四个问题：原来有什么不足、我怎样修改、修改后解决了什么、现在还剩下什么限制。

## 1. 改造目标和基本原则

我的目标不是单纯把某个基准数字压低，而是把原来的教学原型改造成一个“能够编译、能够验证、能够解释、能够继续扩展”的量化开发工程。

我采用了下面几条原则：

1. **正确性优先。** 撮合结果不对，再低的延迟也没有意义。
2. **失败必须清楚。** 容量满、参数错和重复订单不能都悄悄变成一个 `false`。
3. **关键内存尽量预先准备。** 避免在最忙的时候临时扩容。
4. **优化要有对照测试。** 不能因为换了一个听起来更高级的数据结构，就直接宣布更快。
5. **不同口径分开报告。** 核心微基准、完整事件路径、压力吞吐不能混成一个数字。
6. **保留来源和边界。** 说明项目来自哪里、借鉴了什么，也说明当前版本还做不到什么。

## 2. 改造后的总体路径

```text
NewOrder / CancelOrder
          │
          ▼
  参数与品种规则校验
          │
     ┌────┴────┐
   不通过      通过
     │          │
RejectEvent     ▼
            固定容量订单号索引
                 │
                 ▼
        与对手最优价格逐笔撮合
                 │
       ┌─────────┴─────────┐
    完全成交             尚有剩余
       │                    │
  释放临时订单       从共享价格层池取层
                            │
                    加入同价订单队列
                            │
                  生成可配置的事件记录
```

## 3. 第一阶段：让项目在 Visual Studio 中真正可用

### 原来的问题

原代码偏向 GCC/Linux 环境，包含 MSVC 不完全兼容的对齐写法、格式化接口和构建选项。用户即使把仓库下载到 Windows，也不一定能按 README 直接编译。

### 我做的修改

- 补齐 CMake 的 MSVC 分支和编译选项；
- 处理不同编译器的内存对齐写法；
- 修正 Windows 下类型和格式化兼容问题；
- 增加 Visual Studio 生成、编译和运行命令；
- 同时保留 GCC/Clang 和 Linux 构建方式；
- 将测试程序纳入同一套 CMake 工程。

### 改进后的优势

现在可以使用 Visual Studio 2022 的 CMake 生成器构建，也能在 Linux/WSL 下用 GCC 或 Clang 构建。项目不再依赖某一个作者机器上的隐含环境。

### 仍然存在的限制

跨平台“能编译”不表示各平台性能完全相同。MSVC、GCC、Clang 的内联、容器实现和标准库分配器不同，所以性能数字必须附带平台信息。

## 4. 第二阶段：补齐输入校验和明确的拒绝原因

### 原来的问题

原项目对非法价格、非法数量、重复订单号和容量耗尽的处理不够统一。调用方可能只知道失败，却不知道失败原因；个别失败还可能发生在部分状态已经修改之后。

### 我做的修改

我增加并统一了订单拒绝原因，覆盖：

- 订单号为零或订单号重复；
- 价格小于等于零；
- 数量为零；
- 价格不符合 tick；
- 数量不符合 lot；
- 价格超出品种配置范围；
- 单笔数量超过配置限制；
- 订单池耗尽；
- 订单号索引插入失败；
- 撤单目标不存在。

同时调整了基础资源的操作顺序：先完成参数校验，再申请订单对象并登记订单号；只有这两步成功后，才写入“接受”事件。参数、订单池和订单索引失败会生成明确拒绝事件。

这里仍要说明一个边界：订单剩余量需要建立全新价格层时，外层 `std::map` 节点仍可能因为系统内存分配异常而抛出异常。当前版本已经解决了可预见的参数和固定容量失败，但还没有实现对所有系统分配异常的事务式回滚，这也是后续“命令原子性”工作的原因。

### 改进后的优势

- 回测程序可以统计每种拒绝原因；
- 测试可以精确断言失败类型；
- 订单池或订单索引容量耗尽不会伪装成一笔已接受订单；
- 回放时事件语义更一致。

### 仍然存在的限制

当前拒绝规则主要围绕单品种撮合，没有账户资金、持仓、涨跌停、交易时段和监管风控。这些属于后续风险模块，不应该假装已经包含。

## 5. 第三阶段：用固定容量订单号索引替换 `unordered_map`

### 原来的问题

`unordered_map` 查找平均很快，但插入可能分配内存，扩容时还会一次性搬迁大量桶。对普通程序这很方便，对低延迟热路径却会引入偶发抖动。

### 我做的修改

我实现了固定容量、开放寻址的订单号索引：

- 初始化时一次性准备好槽位；
- 插入、查找、删除过程中不再扩容；
- 删除使用后移修复，避免墓碑越积越多；
- 对重复订单号、索引满和不存在订单分别处理；
- 使用长期随机插入、删除和查询验证索引不会逐渐退化。

可以把它理解为提前画好固定数量的停车位。查找订单号时按规则寻找位置，不需要运行中临时扩建停车场。

### 改进后的优势

- 热路径内存使用更可预测；
- 不会在某一笔订单上触发整体扩容；
- 删除后的查找链得到修复，长时间运行更稳定；
- 容量不足会明确拒绝，不会悄悄重新分配。

### 仍然存在的限制

固定容量意味着启动前要做容量规划。装载率过高时，开放寻址也会变慢，所以不能把索引塞到接近 100%。当前实现适合已知上限的单机撮合实验，不是无限增长的数据库。

## 6. 第四阶段：让订单直接知道自己属于哪个价格层

### 原来的问题

撤单时先通过订单号找到订单，再通过订单价格从价格表查找一次价格层。第二次查找是重复工作。

### 我做的修改

我在订单对象中保存所属 `LimitLevel` 的指针，并在挂单时绑定，在成交或撤销离开订单簿时清除。

撤单路径由：

```text
订单号索引 -> 订单 -> 按价格查找价格层 -> 从链表删除
```

变为：

```text
订单号索引 -> 订单 -> 直接找到所属价格层 -> 从链表删除
```

### 改进后的优势

- 少一次价格树查找；
- 从同价链表中摘除订单保持 O(1)；
- 删除逻辑更短，也更容易检查链表关系；
- 撤销中间订单时不需要从队头遍历。

### 仍然存在的限制

指针必须在订单移动、释放和价格层销毁前正确解绑。因此我增加了内部一致性检查和 AddressSanitizer 测试；这个优化不是“加一个指针就结束”，还需要生命周期规则配合。

## 7. 第五阶段：修正价格精度和品种配置

### 原来的问题

原项目采用整数价格，这个方向正确，但默认 tick 与示例中两位小数价格的语义曾不完全一致。整数能避免浮点误差，却不能自动保证每个金融品种的最小变动单位正确。

### 我做的修改

新增 `InstrumentConfig`，将以下规则集中配置：

- 价格缩放方式；
- 最小价格变动 `tick_size`；
- 最小交易单位 `lot_size`；
- 最低和最高允许价格；
- 最大单笔数量。

默认价格缩放采用一元等于 10,000 个内部单位，默认 tick 调整为 100，也就是 0.01 元。下单进入撮合前会验证价格和数量是否落在规则网格上。

### 改进后的优势

- 示例价格、内部整数和校验规则含义一致；
- 换品种时不用到处改魔法数字；
- 回测能更接近交易所真实的最小价格和数量规则；
- 错误配置更容易被测试发现。

### 仍然存在的限制

当前配置仍是单品种级别，尚未包含动态交易时段、不同价格区间采用不同 tick、公司行为和合约换月等复杂规则。

## 8. 第六阶段：将价格层池真正接入主撮合路径

### 原来的问题

订单对象已池化，但新价格出现时，价格层仍可能单独创建。只在旁边写一个没有被主路径使用的对象池，对实际性能没有帮助。

### 我做的修改

- 增加固定容量、共享的 `LimitLevelPool`；
- 买方和卖方价格层从同一个池中取得对象；
- 价格层变空时归还池；
- 价格层对象保存池内编号，便于 O(1) 归还；
- 增加重复释放、错误归属和池耗尽检查；
- 修复容器移动后价格层内部所有者指针的重新绑定；
- 将池化结构接入 `OrderBook` 的真实新单、成交和撤单路径，而不是只做独立样例。

### 改进后的优势

- `LimitLevel` 对象本身不再频繁构造和释放；
- 买卖两侧可以共享容量，减少一侧空闲而另一侧耗尽；
- 价格层容量变得可计算、可拒绝、可测试；
- 长时间价格层反复出现和消失时，生命周期更清楚。

### 一个必须诚实说明的结果

这一改造没有让“价格层反复创建和删除”的基准出现数量级提升。原因是外层有序索引目前仍使用 `std::map<Price, LimitLevel*>`，`std::map` 自己的红黑树节点仍可能分配和释放。

也就是说，我们池化了抽屉本身，但保存“价格到抽屉地址”的树节点还没有池化。该改造主要提升了容量控制、生命周期安全和后续可替换性，不能宣传成已经实现整个价格路径零分配。

## 9. 第七阶段：优化价格层访问，但保留正确的结构边界

### 原来的问题

每次取最优价、查询价格层或删除空层都经过通用容器接口。某些连续撮合会重复读取同一最优价格。

### 我做的修改

- 继续由 `PriceLevelStore` 的有序结构维护最优买卖价；
- 将配置价格区间内“已知价格找已有层”接入连续指针 `PriceLadder`；
- 缓存最近使用的买方和卖方价格层，减少重复同价查找；
- 对连续成交、空层删除和下一最优层切换增加专门测试；
- 尝试过插入 hint、`lower_bound` 合并和更激进的快速删除路径；
- 对没有稳定收益或使代码更脆弱的尝试进行了回退。

### 改进后的优势

主撮合代码通过 `PriceLevelStore` 管理有序目录，通过 `PriceLadder` 加速配置范围内的已有层查找。后续可以在尽量不改撮合规则的情况下继续替换最优价维护结构，最优价切换也有明确的测试保护。

### 为什么没有为了数字强行保留所有优化

有些微优化在一次测试中变快，换一轮、换一组价格或换一个编译器又变慢。低延迟工程不能只挑最好看的一次结果。我保留了稳定且易验证的改动，放弃了收益不稳定、增加错误风险的技巧。

## 10. 第八阶段：重新设计事件路径和性能口径

### 原来的问题

事件容器扩容会污染单笔延迟；但完全关闭事件又不能代表实际业务路径。原项目没有把两种用途清楚分开。

### 我做的修改

- 事件日志支持预留容量；
- 预留容量可配置；
- 支持关闭事件记录，用于测纯撮合核心；
- 记录完整事件的基准和关闭事件的核心基准分别报告；
- 为日志容量耗尽和拒绝事件补充测试；
- 修正接受、成交、撤销和拒绝事件的先后顺序。

### 改进后的优势

现在看到一个延迟数字时，可以回答它是否包含事件生成。事件扩容不再轻易混入预热后的稳定样本，基准口径更清楚。

### 仍然存在的限制

当前事件容器是进程内记录，不等于生产系统中的持久化日志。真正写磁盘、复制到备用节点或发送行情会带来更高成本，需要单独设计异步流水线。

## 11. 第九阶段：让回放从“概念”变成可验证闭环

### 原来的问题

早期回放对事件类型、输入校验、逻辑时间和完整状态覆盖不够。读取文本时若接受格式宽松，还可能把坏数据当成正常数据继续执行。

### 我做的修改

- CSV 解析支持 `NEW`、`CANCEL`、`TRADE`、`REJECT`；
- 严格检查列数、数值范围、买卖方向和事件字段；
- 回放使用与实时路径相同的 `InstrumentConfig`；
- 将当前逻辑时间纳入 `state_hash`；
- 比较订单簿价格、数量、队列顺序、索引关系和逻辑时间；
- 对空行、坏数字、未知事件、缺失字段和越界值增加失败测试；
- 增加回放后继续下单的测试，确认恢复后的引擎仍可工作。

### 改进后的优势

- 相同配置和相同输入能够得到一致状态；
- 坏输入不会悄悄污染回测；
- 状态哈希比只比较成交量更严格；
- 回放与日常撮合共用规则，减少两套逻辑逐渐不一致。

### 仍然存在的限制

CSV 适合阅读和调试，不适合大规模生产恢复。它体积大、解析慢，也缺少版本号、校验和与原子落盘保证。后续应增加二进制命令日志和快照，但保留 CSV 作为可读测试格式。

## 12. 第十阶段：增加全量内部一致性检查

### 原来的问题

订单簿同时维护多个结构，只看对外结果可能发现不了内部已经损坏。例如订单还在链表，却不在订单号索引里；或者价格层汇总数量与订单数量之和不一致。

### 我做的修改

新增 `check_invariants()`，在测试中检查：

- 买方价格顺序和卖方价格顺序正确；
- 空价格层不会残留在价格表中；
- 每个层的头尾指针和前后链接一致；
- 同价订单都具有正确的价格和方向；
- 层内订单数量之和等于汇总数量；
- 每笔挂单都能从订单号索引找到；
- 索引里的每笔订单确实位于某个价格层；
- 订单、价格层和索引使用量互相对应；
- 对象池的使用状态与实际对象一致。

### 改进后的优势

随机压力测试不再只问“有没有崩溃”，还会在每个阶段检查结构有没有悄悄损坏。它是后续大改数据结构时的重要安全网。

### 仍然存在的限制

全量检查需要遍历全部订单，因此不能放进每一笔生产热路径。它适合单元测试、调试构建和离线审计。

## 13. 第十一阶段：建立分层测试体系

当前版本已经形成以下测试层次：

| 测试层 | 当前内容 | 主要目的 |
|---|---|---|
| 单元测试 | 19 组 | 验证价格优先、时间优先、成交、撤单、拒绝、容量和回放等固定场景 |
| 属性/随机测试 | 5 组 | 生成大量不同操作，持续检查不变量和参考结果 |
| CTest | 3 个入口 | 让构建系统统一执行核心、属性和回放测试 |
| AddressSanitizer | MSVC/Linux 可用 | 检查越界、释放后使用、双重释放等内存错误 |
| 百万订单压力 | 长时间混合下单撤单 | 观察吞吐、池容量、索引删除和长期稳定性 |
| 基准测试 | 多种路径 | 分开观察核心、撤单、价格层抖动和完整延迟分布 |

测试覆盖的关键业务包括：

- 买卖价格优先；
- 同价格时间优先；
- 部分成交和完全成交；
- 一笔订单跨多个价格层成交；
- 撤销队头、队中和队尾订单；
- 重复订单号和不存在订单；
- 订单池耗尽、订单索引失败、事件预留配置和价格层池生命周期；
- 非法 tick、lot、价格和数量；
- 移动构造后的内部指针安全；
- 回放一致性和坏文件拒绝；
- 大量插入删除后的索引可用性。

## 14. 第十二阶段：重新建立诚实的性能测试

### 原来的问题

只报告一个最好看的纳秒数字，很容易忽略场景差异和尾延迟。

### 我做的修改

我将性能拆成多个场景：

1. **核心批量下单：** 关闭事件、数据预热，观察最短主路径；
2. **撤单：** 已知订单号的撤销路径；
3. **价格层 churn：** 不断创建和清空价格层；
4. **完整路径：** 保留事件和真实状态更新，统计中位数、P99、P99.9；
5. **百万订单混合压力：** 观察长时间吞吐而不是单笔计时。

当前在本机 Release 构建中的代表性范围是：

| 场景 | 结果范围 | 应怎样理解 |
|---|---:|---|
| 核心批量路径多轮中位数 | 约 40–50 ns/单；本轮 41.597 ns | 预热、关闭事件、特定输入分布，不等于生产全链路 |
| 单轮批量范围 | 本轮约 38.662–51.169 ns/单 | 最低单轮可作为研究线索，不能当稳定承诺 |
| 撤单核心路径 | 约 18–30 ns/单 | 订单已存在且索引命中 |
| 价格层反复创建/清空 | 多轮约 66–86 ns/次；本轮 85.78 ns | 仍包含 `std::map` 节点成本，波动也比最短路径明显 |
| 百万订单混合压力 | 约 640–680 万操作/秒 | 更适合看长时间吞吐 |
| 完整路径 P99 | 数百 ns | 会随事件、成交分布和系统调度变化 |
| 完整路径 P99.9 | 约 1–3 μs | 尾部会受操作系统、缓存和容器慢路径影响 |

这些数字只代表当前机器、当前编译器和当前场景。项目没有再使用“稳定 30 ns”或“每秒 5000 万真实订单”这样的笼统表述。

本轮 Windows 逐笔测试的 P50 曾显示为 `0 ns`。这不是零成本，而是单笔操作短于计时器的可见粒度；因此我主要用 100,000 笔一批、重复 7 轮的批量平均观察核心路径，用逐笔样本观察 P99/P99.9。这个现象也说明，纳秒级报告必须同时审计计时方法。

## 15. 修改前后的集中对比

| 方面 | 原项目 | 当前版本 |
|---|---|---|
| Windows 构建 | 兼容性不足 | 支持 VS2022/CMake/MSVC |
| 订单号索引 | `unordered_map`，可能扩容 | 固定容量开放寻址，不在热路径扩容 |
| 索引删除 | 依赖通用容器 | 后移修复，长期删除不堆积墓碑 |
| 撤单找层 | 按价格再次查找 | 订单保存所属层指针，直接摘链 |
| 价格层对象 | 生命周期分散 | 共享固定容量池，主路径实际使用；异常不变量会立即终止 |

| 性能表述 | 亮眼单点数字 | 报告场景、范围和尾部延迟 |

## 16. 哪些尝试没有达到预想效果

改造过程中并不是每个改变都会变快。以下结果尤其值得记录：

### 16.1 价格层池化没有消除全部分配

原因是 `std::map` 树节点仍会分配。池化的价值主要体现在层对象生命周期、容量控制和安全性，下一步需要替换或定制外层价格索引，才能进一步降低 churn 延迟。

### 16.2 某些插入 hint 只在特定价格序列有效

当订单价格分布与 hint 假设一致时可能更快，价格跳动后可能增加判断或走错分支。最终没有为了单一基准保留不稳定策略。

### 16.3 单次最好结果不能稳定复制

Windows 调度、CPU 降频/升频、缓存状态和后台进程都会影响几十纳秒级测试。因此当前文档报告范围与分位数，不把一次最低值当成系统能力。

### 16.4 关闭事件的核心路径不能替代完整业务路径

关闭事件有助于研究数据结构极限，却不能代表真实回测需要的可审计结果。因此两个口径都保留，不能只展示更好看的一个。

## 17. 当前版本已经解决什么、还没有解决什么

### 已经解决

- 可在声明环境中编译运行；
- 基本限价单撮合、部分成交、跨档成交和撤单正确；
- 容量和非法输入有明确失败路径；
- 订单与价格层对象主要使用固定池；
- 订单号索引热路径不扩容；
- 回放能严格验证状态一致性；
- 有内部不变量、随机测试和内存检查；
- 性能数据按口径诚实披露。

### 尚未解决

- `std::map` 节点仍可能在价格层变化时分配；
- 事件尚未形成带校验和、版本和快照的持久化恢复协议；
- 仅支持基础限价单和撤单，尚无 IOC、FOK、PostOnly、改单和自成交保护；
- 尚无账户资金、仓位和交易时段风控；
- 主要是单品种、单进程模型；
- 尚未接网络、真实交易所协议和行情发布；
- 30 ns 仍只是受限微基准中的探索目标，不是完整路径承诺。

下一步如何继续改进，详见：[当前项目的后续改进路线](03-当前项目的后续改进路线.md)。
