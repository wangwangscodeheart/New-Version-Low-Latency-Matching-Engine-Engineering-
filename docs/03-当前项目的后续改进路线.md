# 当前项目的后续改进路线

> 这份文档只写“还没有完成、下一步准备做”的内容。它不是功能宣传页，而是一份带优先级、选择理由和验收条件的工程计划。

## 1. 当前版本处在什么位置

当前项目已经完成了基础限价撮合、撤单、固定容量订单索引、订单池、价格层池、事件记录、严格回放、内部一致性检查和多层测试。作为一个量化开发学习项目，它已经能清楚展示数据结构、正确性和性能之间的关系。

但如果把目标提高到“更接近真实交易系统”，主要还缺三类能力：

1. **恢复可靠性：** 进程异常退出后，怎样确认最后恢复到了哪一笔命令；
2. **热路径稳定性：** 怎样继续减少动态分配和尾部抖动；
3. **交易语义完整性：** 怎样支持更多真实订单类型、账户规则和多品种。

我会按正确性风险从高到低安排，而不是先做最容易展示的功能。

## 2. 优先级总览

| 优先级 | 工作 | 为什么先做 | 完成标志 |
|---|---|---|---|
| P0 | 版本化命令日志、校验和、快照恢复 | 数据恢复错误比性能慢更危险 | 任意截断/损坏日志都能检测，恢复状态与原状态一致 |
| P0 | 命令原子性与容量边界 | 防止一笔订单只执行一半 | 所有失败场景都不改变有效订单簿 |
| P0 | 安全算术与配置持久化 | 防止金额溢出、配置错配 | 边界属性测试和恢复配置指纹全部通过 |
| P1 | 替换 `std::map` 热价格路径 | 当前最大可见分配来源 | 活跃价格范围内挂单/撤单不再分配树节点 |
| P1 | 有界事件环形缓冲区 | 避免日志扩容污染尾延迟 | 满载行为明确，热路径无扩容 |
| P1 | 增加真实订单语义 | 更贴近量化策略执行 | IOC/PostOnly/Replace/STP 等都有规则和测试 |
| P2 | 多品种单写者分片 | 接近实际部署结构 | 多品种互不共享热锁，可独立恢复 |
| P2 | 行情快照与增量序列 | 服务回测和行情消费者 | 快照+增量可重建一致 L2/L3 状态 |
| P3 | 网络协议、账户风控和主备复制 | 属于更完整交易基础设施 | 单独模块化实现并进行故障注入 |

## 3. P0：先把恢复链路做可靠

### 3.1 当前不足

现在的 CSV 回放适合人读和测试，但不适合作为可靠恢复协议：

- 文本解析开销大；
- 没有清楚的格式版本；
- 文件最后半条记录可能是进程异常退出留下的；
- 没有每条或每块校验和，无法可靠区分“数据合法”和“文件已损坏”；
- 从第一笔开始重放，订单很多时恢复时间太长；
- 配置不一致时，可能用错误的 tick/lot 回放旧数据。

### 3.2 计划方案

新增版本化二进制命令日志，记录进入撮合引擎的命令，而不是把撮合结果再次当成输入。每条记录至少包含：

```text
文件头：魔数 + 格式版本 + 品种配置指纹
记录头：记录长度 + 序列号 + 命令类型 + 逻辑时间
记录体：New / Cancel / Replace 等字段
记录尾：校验和
```

同时增加周期性快照：

1. 保存当前完整挂单状态、下一个序列号和品种配置；
2. 恢复时先加载最近一份有效快照；
3. 再回放快照之后的命令日志；
4. 遇到最后一条不完整记录时停在上一条完整记录；
5. 中间记录校验失败则明确报错，不能悄悄跳过。

### 3.3 为什么记录命令而不是只记录成交结果

撮合引擎的状态由“收到哪些命令以及它们的顺序”决定。只记录最终成交，无法恢复那些仍然挂在订单簿里的订单，也难以重现拒绝原因和时间优先顺序。

### 3.4 验收条件

- 正常日志回放后 `state_hash` 一致；
- 日志在任意字节位置截断时，不读取半条命令；
- 任意一位被翻转时能够发现校验失败；
- 快照加增量回放与全量回放状态一致；
- 配置指纹不同必须拒绝恢复；
- 恢复完成后继续下单，序列号和时间顺序正确。

## 4. P0：保证一条命令要么全成，要么全失败

### 4.1 当前不足

当前版本已经修复了多处先写事件再发现失败的问题，但未来加入 Replace、IOC、持久化和事件环形队列后，资源依赖会变多。需要把命令原子性变成明确设计，而不能靠每个分支人工记忆。

### 4.2 计划方案

每条命令分成三个阶段：

```text
预检查：参数、订单号、容量、配置、算术范围
预留：需要的订单槽、价格层槽、事件槽
提交：修改订单簿并一次性发布结果
```

如果预检查或预留失败，释放已经预留但尚未提交的资源，订单簿状态保持不变。提交阶段只执行已确认不会失败的步骤。

### 4.3 事件缓冲区满时怎样处理

必须在两种策略中明确选择，不能随机丢事件：

- **严格模式：** 没有足够事件空间就拒绝命令，保证所有状态变化都有事件；
- **基准模式：** 明确关闭事件，测纯撮合核心。

不采用“订单照常成交、事件能写多少写多少”的方式，因为这会破坏审计和回放。

### 4.4 验收条件

对订单池、价格层池、索引和事件槽分别做故障注入。任意一步失败后：

- 活跃订单集合不变；
- 最优买卖价不变；
- 池使用计数不变；
- 状态哈希不变；
- 只有一条明确拒绝结果。

## 5. P0：补齐安全算术和配置生命周期

### 5.1 当前不足

价格和数量本身可能都没有越界，但计算成交额 `price × quantity` 时可能溢出。配置如果只存在程序启动参数里，恢复旧日志时也可能误用新规则。

### 5.2 计划方案

- 所有乘法和加法在更新前进行上界检查；
- 内部成交额使用更宽的整数或显式 checked arithmetic；
- 禁止使用浮点数作为订单簿价格键；
- `InstrumentConfig` 生成稳定指纹并写入日志与快照；
- 配置修改使用新版本和生效序列号，不允许运行中悄悄覆盖；
- 对极大价格、极大数量和边界前后一个单位做属性测试。

### 5.3 为什么不直接全部使用大整数库

任意精度整数更通用，但热路径成本更高、内存布局也更复杂。对于已知交易品种，优先通过业务上限证明 64 位或 128 位中间值安全；只有确实需要任意精度时才引入更重工具。

## 6. P1：替换 `std::map` 的活跃价格路径

### 6.1 当前不足

现在价格层对象已经池化，配置价格区间内也已有连续指针 `PriceLadder`，能够按一个已知价格 O(1) 找到已有层。但最优价选择和完整有序成员关系仍由 `std::map` 负责，树节点会在新价格出现时分配。树查找还会跳过多个不连续内存地址，容易发生缓存未命中。这是当前继续压低价格层 churn 延迟的主要障碍。

### 6.2 候选方案比较

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| 继续使用 `std::map` | 简单、正确、价格范围无限制 | 节点分配、指针跳转、尾延迟不稳定 | 保留为通用回退路径 |
| 给 `std::map` 定制节点分配器 | 改动相对小，可减少系统分配 | 仍是树结构，查找缓存局部性一般 | 可作为中间步骤 |
| 扩展现有稠密价格梯 | 已能按 tick 直接定位；继续增加活跃位图和最优档查找 | 价格范围大时占内存 | 适合有明确价格带的品种 |
| 稀疏哈希 + 最优价结构 | 避免大数组 | 找下一个最优价更复杂 | 适合价格范围大但活跃档少 |
| 分段/混合价格梯 | 常用范围走数组，远端走稀疏结构 | 实现与测试复杂 | 当前最推荐的长期方案 |

### 6.3 推荐实现

在现有 `PriceLadder` 上升级为“活跃价格带稠密数组 + 活跃位图 + 远端价格回退结构”：

- 将价格除以 tick 转成档位编号；
- 保留常见价格区间的连续数组直接定位价格层；
- 使用位图或分层位图快速寻找下一个有订单的档位；
- 让范围内最优价选择不再必须访问 `std::map`；
- 极远价格暂存到稀疏回退结构；
- 价格带移动时在安全点重建，不在单笔热路径大规模搬迁；
- 保留 `PriceLadder` 接口，使撮合规则无需跟着重写。

### 6.4 为什么不立刻彻底删除 `std::map`

不同品种价格范围差别很大。如果没有先测真实数据分布，直接申请巨大数组可能用大量内存换来很少收益。因此先用历史订单数据统计：

- 活跃价格带宽度；
- 价格跳空频率；
- 同时存在的价格层数量；
- 最优价移动距离；
- 远端挂单比例。

有数据后再确定数组大小和回退比例。

### 6.5 验收条件

- 常用价格带内新建和删除价格层无堆分配；
- 与当前 `std::map` 版本逐命令结果完全一致；
- 随机价格、极端跳价和全部空层切换测试通过；
- churn 中位数和 P99 都有稳定改善；
- 不能只在顺序递增价格这一种基准中变快。

## 7. P1：将事件改为有界环形缓冲区

### 7.1 当前不足

预先 `reserve` 能减少扩容，但事件总量超过预留值时仍会增长。长期运行时还会一直占用更多内存。

### 7.2 计划方案

- 使用固定容量、连续内存的单生产者环形缓冲区；
- 撮合线程只负责写事件，不做磁盘或网络等待；
- 消费线程异步批量持久化或发布行情；
- 每个事件带连续序列号，消费者可以发现丢失；
- 设置高水位监控；
- 缓冲区满时按严格模式拒绝命令，不能覆盖尚未消费事件。

### 7.3 关键安全点

“异步”不等于可以忽略数据丢失。生产者发布事件前要完成内容写入，消费者读取后再推进可复用位置。即使当前先实现单线程模拟，也要把所有权规则写清楚后再引入原子变量。

## 8. P1：增加更接近真实交易的订单语义

当前只支持基础限价单和撤单。建议按下面顺序增加：

### 8.1 IOC

立即成交能够成交的部分，剩余部分自动撤销，不进入订单簿。它实现简单，又能体现“成交后剩余量处理”的差异。

### 8.2 PostOnly

订单只能挂在订单簿上；如果进入后会立即成交，则拒绝。量化做市常用它避免主动吃单。

实现时必须先判断是否穿过对手最优价，不能先成交再撤回。

### 8.3 Replace / Cancel-Replace

修改价格或增加数量通常应失去原时间优先级；只减少数量是否保留优先级要由市场规则配置。不能直接在原订单对象上随便改字段，否则会破坏队列公平性。

### 8.4 自成交保护（STP）

为订单增加账户或交易主体标识。当买卖双方属于同一主体时，按配置执行取消新单、取消旧单或双方都取消，避免自己和自己成交。

### 8.5 FOK 和市价保护

FOK 要求整笔立即成交，否则全部拒绝。需要先扫描可成交深度或构建累计深度辅助结构，再提交实际成交。

真正的“无限价格市价单”风险太高，更推荐使用带保护价的 IOC，让最坏成交价格明确可控。

### 8.6 验收方法

每种新订单类型都要先写规则表，再写固定场景、随机参考模型和回放测试。不能只在演示程序中跑通一次。

## 9. P2：多品种和单写者分片

### 9.1 推荐结构

```text
接入/解析线程
      │
      ▼
按 symbol 哈希或配置路由
  ┌──────┬──────┬──────┐
  ▼      ▼      ▼
分片 0  分片 1  分片 2
单线程  单线程  单线程
多个簿  多个簿  多个簿
```

每个订单簿仍由一个撮合线程顺序修改，不在同一订单簿内部加大量锁。不同品种分布到多个分片并行处理。

### 9.2 为什么推荐单写者

同一个订单簿的价格时间优先本来就要求确定顺序。让多个线程同时修改一个簿，会引入锁竞争、复杂内存模型和顺序争议。按品种分片更容易获得并行度，也更容易回放。

### 9.3 需要新增的内容

- 全局输入序列与分片序列；
- symbol 到 `InstrumentConfig` 的映射；
- 每个分片独立容量、日志和快照；
- 热门品种迁移策略；
- 跨品种策略不能直接阻塞撮合线程。

## 10. P2：行情快照和增量发布

回测和策略通常不需要看到引擎内部所有指针，只需要标准化行情：

- L1：最优买价、最优卖价及数量；
- L2：各价格档汇总数量；
- L3：每笔订单级别变化。

计划为每次变化生成带序列号的增量，同时支持周期性快照。消费者流程为：

```text
读取快照序列 N
接收 N+1、N+2、N+3 ... 增量
若中间缺号，停止使用并重新请求快照
```

这样量化策略或可视化程序才能可靠重建订单簿，而不是猜测是否漏了一条消息。

## 11. P3：账户风控、网络和高可用应独立成模块

这些都很重要，但不适合现在直接塞进 `MatchingEngine::submit()`：

- **账户风控：** 余额、持仓、单日限额、最大敞口；
- **交易日规则：** 开闭市、涨跌停、停牌；
- **协议接入：** TCP/UDP、FIX 或交易所私有二进制协议；
- **高可用：** 主备复制、故障切换、重复命令去重；
- **监控：** 队列水位、延迟分位数、拒绝原因、快照进度。

合理的做法是保持撮合核心接受已经结构化的命令，把解析、风控和持久化放在明确边界之外。这样既便于测试，也避免每改一个网络协议就影响撮合规则。

## 12. 性能测试还要怎样改进

### 12.1 当前不足

Windows 桌面环境会受到线程迁移、后台进程、CPU 睿频和计时器开销影响。当前数字适合工程比较，但还不足以作为硬件能力结论。

### 12.2 下一步测试规范

- 固定 CPU 型号、内存、操作系统、编译器版本和完整编译参数；
- Release 构建，确认断言和 sanitizer 未混入性能版本；
- 先预热数据和代码；
- 将测试线程绑定到固定物理核心；
- 记录 CPU 频率策略和是否开启 SMT；
- Linux 下同时使用 `steady_clock`、TSC 校准和 `perf` 计数器交叉检查；
- 至少报告中位数、P90、P99、P99.9、最大值和样本数；
- 分别测试空簿挂单、同价挂单、立即成交、跨档成交、撤单、价格层 churn；
- 使用固定随机种子和真实分布样本；
- 保存原始结果，不只保留汇总数字。

### 12.3 对 30 ns 目标的态度

可以继续探索 30 ns，但必须限定为明确的微基准，例如：

> 数据已在缓存中、无事件、无动态分配、无价格层创建、单线程批量提交的一种限价挂单路径。

如果未来达到，应同时公开完整路径的 P99/P99.9，不能把最短微基准替代整个系统能力。

## 13. 分阶段里程碑

### M1：恢复正确性

- 版本化二进制命令日志；
- 校验和与截断检测；
- 快照和增量恢复；
- 配置指纹；
- 故障注入测试。

**交付标准：** 随机运行后在任意位置模拟崩溃，恢复出的最后完整状态可证明正确。

### M2：活跃价格路径无分配

- 统计真实价格分布；
- 实现混合价格梯；
- 保留旧结构作为参考模型；
- 对照正确性和性能。

**交付标准：** 常用价格带内没有堆分配，中位数和 P99 均稳定优于现版本。

### M3：真实订单语义

- IOC；
- PostOnly；
- Replace；
- STP；
- FOK/保护市价。

**交付标准：** 每种规则有明确文档、单元测试、属性测试和回放测试。

### M4：回测可用性

- 多品种配置；
- 标准历史输入转换；
- L2/L3 行情输出；
- 快照与增量序列；
- 回测统计接口。

**交付标准：** 策略程序能够用统一接口驱动多个品种并可靠重建行情。

### M5：部署与性能实验

- 单写者分片；
- 固定核、NUMA 和硬件环境报告；
- 异步事件消费；
- 持续性能回归门槛；
- 故障与积压监控。

**交付标准：** 正确性测试、恢复测试和性能回归可以在 CI/固定测试机重复执行。

## 14. 我暂时不会做的“看起来高级”功能

为了控制项目范围，下面这些内容不应在基础正确性完成前抢先加入：

- 为了简历关键词直接接 DPDK/RDMA；
- 在单个订单簿内部堆很多线程和锁；
- 没有真实行情分布就申请巨型价格数组；
- 没有恢复协议就先做主备切换宣传；
- 只追求最好一次 30 ns，忽略 P99.9；
- 把撮合、风控、网络、策略和数据库写进一个大类。

这些技术不是没有价值，而是需要在明确问题、测试数据和模块边界之后使用。当前阶段更有价值的是把每个已有结论做实。

## 15. 主要风险和应对方式

| 风险 | 可能后果 | 应对 |
|---|---|---|
| 新价格梯优化破坏价格优先 | 撮合错误 | 旧实现作为参考模型，逐命令差分测试 |
| 固定容量估算过小 | 高峰拒单 | 高水位监控、离线容量回放、启动配置校验 |
| 事件消费者跟不上 | 环形队列满 | 严格背压、批量消费、容量告警，不静默覆盖 |
| 快照与日志序列错位 | 恢复出错误状态 | 序列号、配置指纹、校验和、故障注入 |
| 为性能使用不安全指针 | 隐蔽内存错误 | 所有权规则、ASan、随机 churn、移动语义测试 |
| 微基准过拟合 | 对真实场景没有收益 | 多种价格与成交分布、报告全分位数 |
| 功能增长导致核心臃肿 | 难以维护和验证 | 协议、风控、持久化与撮合核心分层 |

## 16. 最终目标

这个项目下一阶段最重要的，不是继续增加宣传词，而是逐步形成下面这条证据链：

```text
规则写清楚
   ↓
实现边界清楚
   ↓
固定测试 + 随机测试证明正确
   ↓
崩溃与容量失败仍然可控
   ↓
同样输入能够恢复到同样状态
   ↓
在明确环境和场景下测量性能
```

只有沿着这条路线继续，项目才能从“有趣的低延迟代码”逐渐变成“可信的量化撮合工程”。
