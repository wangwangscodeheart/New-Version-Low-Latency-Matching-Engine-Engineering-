# 当前项目的后续改进路线

> 本文只列最终代码收官后仍未完成的内容。它不是本轮实施计划，也不表示这些功能已经存在。每项工作都应在独立 Sprint 中重新评审范围，再决定是否开发。

## 1. 当前基线已经完成什么

当前项目已经形成一个结构清楚的最小架构基线：

- `Command` 与 `EngineEvent` 分离；
- `process(const Command&)` 统一入口；
- `CommandSequence`、`EventIndex`、`PrioritySequence` 各自承担一种顺序语义；
- 单品种限价撮合和撤单；
- 固定订单池、固定 ID 索引、价格层池和混合价格目录；
- Command 重执行 Replay 全量验证；
- 轻量内存 Snapshot 恢复；
- `check_invariants()`、完整 `OrderBookState` 和辅助 `state_hash()`；
- Release、随机属性测试、Snapshot 测试和 ASan。

这条基线适合学习和回测内核实验。接下来不是“继续往一个类里塞功能”，而是根据用途选择独立方向。

## 2. 仍未解决的问题总览

| 方向 | 当前缺口 | 对学习/回测的影响 | 建议优先级 |
|---|---|---|---|
| 最终基准复测 | 架构收官 HEAD 尚未跑完整性能矩阵 | 不能把旧性能提交数据当最终 HEAD 新测结果 | P0 |
| 异常原子性 | `std::map` 节点分配异常未形成事务回滚 | 极端内存失败下缺少严格承诺 | P0 |
| 安全算术 | 成交额等扩展计算尚无统一 checked arithmetic | 接入费用/金额后可能溢出 | P0 |
| 参考正确性 | 没有独立 Reference Engine 和差分测试 | 大改结构时缺少第二套实现交叉验证 | P1 |
| 回测适配 | 没有行情、手续费、滑点、交易时段适配层 | 不能单独完成完整策略回测 | P1 |
| 持久化 | 没有 Journal、磁盘 Snapshot、校验和和崩溃恢复 | 进程退出后不能可靠恢复 | P2 |
| 订单语义 | 没有 IOC/FOK/PostOnly/Replace/STP | 与真实执行规则仍有差距 | P2 |
| 热路径结构 | 新价格层仍使用 `std::map` 节点 | 新档和跨档尾延迟较高 | P2 |
| 多品种部署 | 没有路由、分片和跨品种配置管理 | 只能运行单个订单簿实例模型 | P3 |
| 生产接入 | 没有网络、风控、行情发布和主备 | 不能直接用于真实资金 | P3 |

P0/P1/P2 表示建议顺序，不表示已经授权开始开发。

## 3. P0：在最终架构提交上重新建立性能基线

### 为什么先做

已保存的最佳性能矩阵对应 `e4d59e2`。后续又增加了统一 Command 入口、sequence gate、新事件模型和架构验证。虽然这些变化有清楚的正确性价值，但尚未用同一方法测量最终 HEAD。

因此当前文档只能说：性能阶段的三个窄场景达到约 25–27 ns；不能说最终架构版本已经重新证明这一数字。

### 建议做法

保持已有脚本和场景不变，在干净构建上记录：

- commit hash；
- CPU、系统、电源模式、编译器和编译参数；
- 是否绑核、是否关闭事件；
- 5 个新进程 × 每进程 7 次；
- 五个微基准的进程中位数；
- Release CTest 和 ASan 结果。

同时再增加“显式 `Command` + 事件开启”的架构成本口径，但不要把它与关闭事件的原微基准混成一个数字。

### 验收标准

- 原性能场景和新架构场景分别输出；
- 原始 CSV/JSON 入库；
- 没有只挑最好一次；
- 若结果退化，先定位是语义成本、编译布局还是系统噪声，不为数字破坏架构。

## 4. P0：处理可预见失败与系统异常的原子边界

### 当前状态

参数错误、订单池满、ID 索引满等可预见失败已有明确路径。sequence gate 失败也不会产生事件或修改状态。

仍需注意：当剩余订单需要创建新价格档时，外层 `std::map` 节点理论上可能因系统内存不足抛出异常。当前代码没有对所有这类分配异常提供完整事务回滚证明。

### 候选方案

1. **给价格目录使用预分配节点资源**：减少提交阶段失败点；
2. **命令三阶段处理**：预检查、资源预留、不可失败提交；
3. **故障注入**：在订单池、层池、索引、事件空间和价格节点处逐点模拟失败；
4. **明确 fail-fast 边界**：若某些内部不变量不可能安全恢复，应终止而不是继续运行损坏账本。

### 验收标准

每个注入点失败后都验证：

- `capture_state()` 不变；
- `last_applied_command_sequence` 是否推进符合该失败所属阶段；
- Event 是否符合准入/业务边界；
- 池和索引使用量不变；
- `check_invariants()` 通过。

## 5. P0：安全算术和配置边界

### 当前状态

价格和数量使用整数，层数量累加已检查溢出；但如果以后计算成交额、手续费、资金和持仓，`price × quantity` 可能在单个输入都合法时仍溢出。

### 建议方案

- 外部十进制价格直接解析为整数，避免 `double` 进入正式输入边界；
- 为乘法、加法和减法建立显式 checked arithmetic；
- 根据品种上限证明 64 位是否够用，必要时用 128 位中间值；
- 配置变更必须有独立版本和生效点，不能运行中静默覆盖；
- 添加最大价格、最大数量和边界前后一个单位的测试。

### 验收标准

极值输入要么得到精确结果，要么在任何账本修改前明确拒绝，不能发生整数回绕。

## 6. P1：增加独立参考模型和差分测试

### 为什么需要第二套实现

当前测试和生产实现共享一部分概念。若主实现和测试以同样方式理解错一个规则，现有测试可能一起通过。

Reference Engine 应追求简单而不是快，例如：

- 使用标准容器；
- 不使用对象池和缓存；
- 业务逻辑写得直白；
- 独立生成可比较事件和完整状态。

### Differential Testing 流程

```text
同一批随机 Command
      ├── 当前低延迟引擎
      └── 简单参考引擎
                │
                ▼
逐命令比较 ProcessStatus、EngineEvent 和完整 BookState
```

### 验收标准

- 固定随机种子可复现；
- 覆盖重复/倒退 sequence、业务拒绝、部分成交、跨档、撤单和容量边界；
- 失败时打印最小 Command 前缀，而不是只输出最终哈希；
- 至少在长随机序列和缩减后的最小反例上稳定复现。

## 7. P1：把撮合核心接到真正的回测外层

### 当前项目为什么还不是完整回测器

撮合引擎只回答订单怎样进入订单簿、成交或撤销。策略回测还需要：

- 历史行情或历史订单流输入；
- 策略决策时间与撮合接收顺序；
- 手续费、滑点和最小成交单位；
- 交易时段、停牌、涨跌停和合约规则；
- 策略持仓、现金和损益；
- 多品种结果汇总。

### 推荐边界

不要把这些功能塞进 `OrderBook`。更清楚的层次是：

```text
历史数据适配器
     ↓
回测调度器 / 策略
     ↓ Command
撮合引擎
     ↓ EngineEvent
成交、手续费、持仓与绩效模块
```

`CommandSequence` 由回测调度器分配，外部市场时间作为单独元数据保存，不再改变引擎内部 FIFO 规则。

### 验收标准

- 一个小型历史数据集可重复得到同一 EngineEvent 序列；
- 手续费和滑点不侵入订单簿内部结构；
- 策略状态与订单簿状态可以分别保存和比较；
- 文档明确是 L3 订单级模拟、L2 近似还是简化成交模型。

## 8. P2：持久化恢复必须作为独立 Sprint

### 当前已有和未有

已有：

- 明确 Command 模型；
- 明确 EngineEvent 模型；
- CommandSequence；
- Command 重执行验证；
- 内存 Snapshot。

未有：

- CommandJournal；
- ExecutionJournal；
- Event Application；
- 磁盘 Snapshot；
- checksum、fsync、原子重命名和截断处理；
- 崩溃一致性协议。

### 为什么不能把 CSV 当 Journal

CSV 事件文件可读，但没有：

- 文件格式版本和配置指纹；
- 记录长度和校验和；
- 半条记录检测；
- 写入顺序和落盘保证；
- Command 与 Event 的持久化一致性规则。

### 未来候选流程

```text
CommandJournal（权威输入）
        ↓
OrderBook::process
        ↓
ExecutionJournal（可选审计输出）

恢复：磁盘 Snapshot + Snapshot 后的 CommandJournal 后缀
```

是否实现 Event Application 应单独决定。Command re-execution 与 apply_event 是两种不同恢复模型，不应在没有需求时同时加入。

### 验收标准

- 任意位置截断只恢复到上一条完整记录；
- 中间数据翻转能被校验和发现；
- Snapshot 配置和日志配置不匹配时拒绝；
- 全量 Command 重放与 Snapshot + 后缀重放的完整状态一致；
- 崩溃测试覆盖写入前、写入中、写入后不同点。

## 9. P2：增加真实订单语义

建议每种订单类型独立设计状态机和测试，不要一次全部加入。

| 功能 | 核心规则 | 主要风险 |
|---|---|---|
| IOC | 能成交部分立即成交，剩余取消 | 事件顺序和剩余量处理 |
| FOK | 不能立即全部成交就完全不执行 | 需要提交前扫描可成交量 |
| PostOnly | 会立即成交时拒绝，只允许挂单 | 与价格变化和拒绝原因相关 |
| Replace | 修改价格/数量，通常会失去或调整优先级 | 原子性和 PrioritySequence 规则 |
| STP | 防止同账户自成交 | 需要账户维度和多种处理策略 |

每加入一种功能，都应补 Command、ProcessStatus/RejectReason、EngineEvent、Replay、Snapshot 和 Reference Engine 的对应测试。

## 10. P2：是否继续替换 `std::map`

### 当前事实

已有价格层对象池和 `PriceLadder`，但完整价格排序仍由 `std::map` 负责。性能阶段数据显示：

- 已有同价层约 26.663 ns/order；
- 新建价格层约 73.090 ns/order；
- 扫四档约 186.440 ns/order。

新价格档和跨档路径仍有明显空间。

### 候选方案

| 方案 | 优点 | 缺点 |
|---|---|---|
| 保留 `std::map` | 清楚、任意合法价格、正确性成熟 | 节点分配和指针跳转 |
| map 自定义节点资源 | 改动较小，减少系统分配 | 仍是树结构 |
| 稠密价格梯 + 活跃位图 | 已知价格带内定位和找下一档快 | 宽价格范围占内存 |
| 分段价格梯 + 稀疏回退 | 兼顾热点价格带和远端订单 | 实现和验证复杂 |

在没有真实价格带数据前，不建议为了纳秒直接删除 `std::map`。应先统计活跃档宽度、最优价移动距离、远端挂单比例和层 churn 频率。

### 验收标准

- 常用价格带新建/删除不再系统分配；
- 最优价切换结果与参考引擎一致；
- 范围外订单仍正确；
- 内存成本可计算；
- P50/P99/P99.9 和吞吐都有对照，而不是只看最好值。

## 11. P2：固定容量事件缓冲区

当前 `std::vector<EngineEvent>` 会预留容量，但超过预留仍可扩容。未来如果要求严格热路径无扩容，必须明确选择：

- 严格模式：事件空间不足则在状态修改前拒绝命令；
- 基准模式：明确关闭事件，只测撮合核心；
- 外部消费者模式：使用有界 SPSC 队列，但需要定义背压策略。

不能采用“订单已经修改，事件能写多少写多少”，因为那会破坏审计一致性。

## 12. P3：多品种和生产部署

更接近真实部署时，可以采用“一个订单簿一个单写者”而不是让多个线程争用同一个簿：

```text
入口路由
  ├── Instrument A -> Engine 0
  ├── Instrument B -> Engine 1
  └── Instrument C -> Engine 2
```

随后才考虑：

- CPU 亲和性和 NUMA；
- 每品种独立 sequence 与恢复点；
- 行情增量序列和快照；
- 网络协议与用户态收包；
- 账户风控、主备复制和运维观测。

这些已经属于交易基础设施，不适合为了丰富简历一次性堆入当前学习仓库。

## 13. 哪些事情不应优先做

- 为了再次出现更小数字而删除 sequence 或事件语义；
- 把 `check_invariants()` 塞进每笔热路径；
- 没有真实分布就申请巨大价格数组；
- 同时实现 Journal、Event Recovery、Reference Engine、网络和多线程；
- 用 `state_hash` 代替逐字段验证；
- 把内存 Snapshot 宣传成崩溃恢复；
- 把关闭事件的微基准写成客户到交易所的端到端延迟。
