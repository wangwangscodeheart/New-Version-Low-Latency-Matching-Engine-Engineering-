# 新项目完整介绍与使用说明

> 这份文档从最终代码出发，不要求读者已经熟悉交易系统。它先解释金融含义，再说明数据模型、处理顺序、Replay、Snapshot、构建和测试。

## 1. 项目解决的是什么问题

限价撮合引擎接收“我愿意按什么价格买/卖多少”的命令，维护暂时不能成交的订单，并在买卖价格相遇时决定成交顺序。

它要稳定回答：

- 当前最高买价和最低卖价是多少；
- 一笔新单会与哪些旧订单成交；
- 成交价格和数量是多少；
- 未成交部分排在同价队伍的什么位置；
- 撤单应该删除哪一笔；
- 同一批输入重新执行能否得到完全相同的结果。

本项目只做这个核心，不负责策略收益、账户资金、网络接入或交易所完整业务。

## 2. 先理解几个金融概念

### 2.1 限价单

限价单给出最差可接受价格：

```text
买 100 股，限价 10.00：成交价不能高于 10.00
卖 100 股，限价 10.00：成交价不能低于 10.00
```

当前项目只支持基础限价单和撤单，没有 Market、IOC、FOK、PostOnly 或 Replace。

### 2.2 订单簿

暂时不能成交的订单留下来排队，组成订单簿：

```text
卖方
10.03   100
10.02    80
10.01    50  <- 最优卖价 best ask
----------------
10.00    70  <- 最优买价 best bid
 9.99   120
 9.98    90
买方
```

最高买价叫 best bid，最低卖价叫 best ask。正常静态订单簿应满足 `best_bid < best_ask`；如果两者可以成交，引擎会立即撮合，不应长期留下交叉状态。

### 2.3 主动单和被动单

订单 1 先以 10.00 卖出 100 股并挂在簿中。之后订单 2 以 10.10 买入 40 股：

- 订单 2 主动进入并立即成交，是 aggressive order；
- 订单 1 原来已经挂在簿中，是 passive order；
- 成交价格使用被动订单价格 10.00；
- 订单 1 还剩 60 股。

### 2.4 价格优先、同价 FIFO

- 买方价格更高的先成交；
- 卖方价格更低的先成交；
- 同一价格上，优先序列更小的先成交。

当前版本不再用含义模糊的系统时间决定同价顺序，而是把命令顺序转成明确的 `PrioritySequence`。

## 3. 三层数据模型

最终代码把输入、输出和状态分开。

### 3.1 Command：调用者要求引擎做什么

```cpp
struct NewOrderCommand {
    CommandSequence command_sequence;
    OrderId order_id;
    Side side;
    Price price;
    Quantity quantity;
};

struct CancelOrderCommand {
    CommandSequence command_sequence;
    OrderId order_id;
};

using Command = std::variant<NewOrderCommand, CancelOrderCommand>;
```

`Command` 是输入事实。它不是成交，也不是订单已经挂入订单簿的证明。

### 3.2 EngineEvent：命令实际产生了什么结果

```cpp
using EngineEvent = std::variant<
    TradeEvent,
    OrderRestedEvent,
    OrderCancelledEvent,
    OrderRejectedEvent>;
```

| Event | 含义 |
|---|---|
| `TradeEvent` | 主动单与一笔被动单发生一笔成交 |
| `OrderRestedEvent` | 新单成交后还有剩余，并实际进入订单簿 |
| `OrderCancelledEvent` | 一笔活跃挂单被成功撤销 |
| `OrderRejectedEvent` | 命令已通过 sequence gate，但业务规则不允许执行 |

项目没有 `OrderAcceptedEvent`。原因是四种实际结果已经能够完整表达当前业务：

- 全部主动成交：一个或多个 `TradeEvent`；
- 部分成交后挂单：先 Trade，后 `OrderRestedEvent`；
- 纯挂单：一个 `OrderRestedEvent`；
- 成功撤单：一个 `OrderCancelledEvent`；
- 业务拒绝：一个 `OrderRejectedEvent`。

### 3.3 OrderBookState：引擎现在处于什么状态

`capture_state()` 返回可逐字段比较的 `OrderBookState`：

- 最后消费的 CommandSequence；
- 全部买方价格档和卖方价格档；
- 每档汇总剩余量；
- 每档 FIFO 中全部订单；
- 每笔订单的原始数量、剩余数量和 PrioritySequence；
- 活跃订单数；
- best bid / best ask。

它不暴露内部指针，适合测试和 Replay 比较。

## 4. 三种 Sequence 分别做什么

### 4.1 CommandSequence

表示输入命令的逻辑顺序，规则是：

1. 必须大于 0；
2. 必须严格大于 `last_applied_command_sequence`；
3. 允许跳号，例如 10 后可以直接来 20；
4. 重复、倒退和 0 都在准入阶段拒绝；
5. 通过 gate 后，即使业务拒绝也会推进最后序列。

允许跳号是因为上游可能按分区、过滤或恢复点分配序号；引擎只要求新序列严格向前，不要求连续。

### 4.2 EventIndex

一条 Command 可能扫多个价格档，产生多个 Event。它们都带相同 `CommandSequence`，并用 `EventIndex` 从 0 开始连续排序。

例如命令 40 连续成交三笔并把剩余挂单：

```text
(CommandSequence=40, EventIndex=0) TradeEvent
(CommandSequence=40, EventIndex=1) TradeEvent
(CommandSequence=40, EventIndex=2) TradeEvent
(CommandSequence=40, EventIndex=3) OrderRestedEvent
```

### 4.3 PrioritySequence

新单真正进入订单簿时保存优先序列。同一价格层按它严格递增，撮合从最小值开始。

它只表达 FIFO 先后，不代表真实世界纳秒时间。`Timestamp` 强类型为了旧代码兼容仍在 `types.hpp`，但不参与当前核心撮合语义。

## 5. 统一处理入口和两类拒绝

### 5.1 API

```cpp
ProcessResult process(const Command& command);
```

返回值：

```cpp
enum class ProcessStatus {
    APPLIED,
    REJECTED,
    SEQUENCE_REJECTED
};

struct ProcessResult {
    ProcessStatus status;
    size_t event_begin;
    size_t event_count;
};
```

`event_begin/event_count` 指向这条命令在引擎事件容器中产生的区间。

### 5.2 Admission rejection

sequence 为 0、重复或倒退：

- 返回 `SEQUENCE_REJECTED`；
- `event_count == 0`；
- 不增加 EngineEvent；
- 不修改订单簿；
- 不推进最后序列。

这表示命令没有被引擎接纳。

### 5.3 Business rejection

命令通过 sequence gate，但订单 ID 重复、价格非法或撤单目标不存在：

- 返回 `REJECTED`；
- 产生一个 `OrderRejectedEvent`；
- 不修改有效挂单集合；
- 推进 `last_applied_command_sequence`。

这表示命令已经被引擎消费，只是业务结果为拒绝。

### 5.4 正常执行

返回 `APPLIED`。事件数量可能不同：

- 纯挂单：1；
- 一次完全成交：1 个 Trade；
- 多档成交：多个 Trade；
- 部分成交后挂单：多个 Trade + 1 个 Rested；
- 成功撤单：1 个 Cancelled；
- 关闭事件记录的基准模式：0，但订单簿仍正常修改。

## 6. 总体架构

```text
调用者 / 回测调度器
       │ Command
       ▼
┌─────────────────────────────────────┐
│ OrderBook::process                  │
│  1. CommandSequence gate            │
│  2. InstrumentConfig 校验           │
│  3. FixedOrderIndex / ObjectPool    │
│  4. PriceLevelStore / PriceLadder   │
│  5. LimitLevel FIFO 撮合或撤单      │
└─────────────────────────────────────┘
       │ EngineEvent
       ▼
调用者读取成交、挂单、撤销或拒绝结果

旁路验证：ReplayEngine -> 全新 OrderBook -> 全字段比较
旁路恢复：SnapshotRecovery -> 全新 OrderBook -> 重建状态
```

## 7. 核心数据结构

### 7.1 整数价格与强类型

项目将一元放大 10,000 倍：

```text
100.00 -> 1,000,000
100.01 -> 1,000,100
```

演示和测试可以使用：

```cpp
Price price = from_double(100.01);
double display = to_double(price);
```

正式外部适配层更适合把十进制字符串直接解析为整数，避免 `double` 的近似值进入引擎边界。

`OrderId`、`Price`、`Quantity`、`CommandSequence`、`EventIndex` 和 `PrioritySequence` 都是不同强类型，底层虽是整数，却不能随意互换。

### 7.2 ObjectPool<Order>

构造 `OrderBook` 时按容量准备订单对象。订单生效时在池内原地激活，完全成交或撤销后归还。

优势：

- 常见路径不为每笔订单单独 `new`；
- 地址稳定；
- 活跃订单内存上限清楚；
- 容量满可以明确拒绝。

代价：启动时占用更多内存，容量需要根据高峰活跃订单数规划。

### 7.3 FixedOrderIndex

撤单先按 `OrderId` 找订单。固定索引采用开放寻址：

1. 对 ID 计算起始槽；
2. 冲突时继续探测；
3. 插入先 `prepare_insert()`，再 `commit_insert()`；
4. 删除后向前修复受影响的探测链。

它避免 `unordered_map` 在热路径 rehash，但不保证永远只访问一个槽。容量越接近满载，冲突成本越高。

### 7.4 LimitLevel 与侵入式 FIFO

每个价格层保存双向链表：

```text
head                                              tail
Order 1(p=10) <-> Order 2(p=20) <-> Order 3(p=30)
```

这里 `p` 表示 PrioritySequence。新挂单进尾部，撮合从头部开始。订单本身保存 `prev/next/parent_level`，因此已知订单地址后可以 O(1) 摘链。

### 7.5 LimitLevelPool

买卖两侧共享固定容量价格层池。新价格第一次出现时取一个层，层内最后一笔订单离开时归还。

它池化的是 `LimitLevel` 对象，不是 `std::map` 的树节点。

### 7.6 PriceLevelStore

买方和卖方各有一个有序价格目录：

- bids 从高到低；
- asks 从低到高；
- map 值指向层池中的 `LimitLevel`。

它是完整价格排序的权威来源，支持配置范围外价格，但新档出现/消失时 map 节点仍可能分配/释放。

### 7.7 PriceLadder

配置价格区间内，价格按 tick 映射到连续指针数组。已知价格查层可以直接计算位置，不必再次走树查找。

默认示意：

```cpp
PriceLadderConfig {
    min_price = 900000,   // 90.00
    max_price = 2100000,  // 210.00
    tick = 100            // 0.01
};
```

超出这段范围的合法价格仍由 `PriceLevelStore` 正确处理。PriceLadder 是快速表，不是价格合法范围；合法范围由 `InstrumentConfig` 决定。

## 8. InstrumentConfig

示例：

```cpp
InstrumentConfig config;
config.tick_size = 100;                  // 0.01
config.lot_size = 100;                   // 100 的整数倍
config.min_price = from_double(1.00).get();
config.max_price = from_double(1000.00).get();
config.max_order_quantity = 1'000'000;
```

当前检查：

- 价格大于 0；
- 价格在 min/max 范围内；
- 价格落在 tick 网格；
- 数量大于 0；
- 数量不超过最大单笔数量；
- 数量落在 lot 网格；
- OrderId 不为 0 且不重复；
- 订单池和 ID 索引仍有容量。

`PriceLadderConfig` 与 `InstrumentConfig` 是两个概念：前者决定快速访问区间，后者决定业务合法性。

## 9. 新订单的完整处理流程

以一笔买单为例：

### 第一步：sequence gate

命令序列必须严格大于最后已消费序列。失败直接返回，不产生事件。

### 第二步：业务校验和资源准备

检查订单 ID、价格、数量和品种规则；准备固定 ID 索引槽和订单池对象。可预见失败产生 `OrderRejectedEvent`。

### 第三步：从最低卖价开始撮合

如果买价低于 best ask，不能立即成交；否则从最低卖价的 FIFO 头开始。

```text
trade_quantity = min(主动单剩余量, 被动单剩余量)
```

每与一笔被动单成交一次，产生一个 `TradeEvent`。被动单完全成交后从链表、ID 索引和订单池删除；空价格层从目录和价格梯删除，层对象归还池。

### 第四步：处理主动单剩余

- 剩余为 0：主动单不进入订单簿；
- 剩余大于 0：找到或创建自己的买方价格层，按 PrioritySequence 加到队尾，并产生 `OrderRestedEvent`。

### 第五步：提交最后命令序列

只要命令通过了 sequence gate，不论业务结果是 APPLIED 还是 REJECTED，都会推进最后序列。

## 10. 跨档成交例子

卖方订单簿：

```text
100.00：Order 1，20
100.50：Order 2，30
101.00：Order 3，50
```

命令 10 提交一笔“101.50 买 80”：

1. 与 Order 1 在 100.00 成交 20，EventIndex 0；
2. 与 Order 2 在 100.50 成交 30，EventIndex 1；
3. 与 Order 3 在 101.00 成交 30，EventIndex 2；
4. 主动买单完全成交，不产生 Rested；
5. Order 3 还剩 20，新的 best ask 是 101.00。

三个 TradeEvent 都带 `CommandSequence(10)`。

## 11. 撤单流程

```text
CancelOrderCommand
       │
       ├── sequence gate 失败 -> SEQUENCE_REJECTED，无事件
       ▼
FixedOrderIndex 查 OrderId
       ├── 不存在 -> REJECTED + OrderRejectedEvent(ORDER_NOT_FOUND)
       ▼
Order::parent_level 直接摘链
       │
       ├── 更新层订单数和总量
       ├── 空层则删除目录并归还层池
       ├── 删除 ID 索引并归还订单对象
       └── OrderCancelledEvent
```

`OrderCancelledEvent` 保存撤销前的方向、价格、剩余数量和 PrioritySequence，方便调用者理解实际取消了什么。

## 12. 最小调用示例

```cpp
#include "commands.hpp"
#include "orderbook.hpp"

#include <iostream>
#include <variant>

int main() {
    InstrumentConfig config;
    config.tick_size = 100;
    config.lot_size = 1;

    OrderBook book(
        10'000,              // 最大活跃订单容量
        true,                // 记录 EngineEvent
        PriceLadderConfig{}, // 快速价格表配置
        2,                   // 事件预留倍率
        config);

    ProcessResult first = book.process(NewOrderCommand(
        CommandSequence(1), OrderId(1001), Side::SELL,
        from_double(10.00), Quantity(100)));

    ProcessResult second = book.process(NewOrderCommand(
        CommandSequence(2), OrderId(1002), Side::BUY,
        from_double(10.00), Quantity(40)));

    if (!first.applied() || !second.applied()) return 1;

    // 第二条命令应产生一笔 Trade，卖单还剩 60。
    for (size_t i = second.event_begin;
         i < second.event_begin + second.event_count; ++i) {
        if (const auto* trade =
                std::get_if<TradeEvent>(&book.engine_events()[i])) {
            std::cout << "trade qty = " << trade->quantity.get() << '\n';
        }
    }

    ProcessResult cancel = book.process(
        CancelOrderCommand(CommandSequence(3), OrderId(1001)));

    return cancel.applied() && book.check_invariants() ? 0 : 1;
}
```

旧接口 `process_new_order()` 和 `process_cancel()` 仍可用，它们自动使用 `last + 1` 的兼容序列。但学习和正式测试建议直接构造 Command，因为显式序列更容易回放和定位问题。

## 13. Command Replay

### 13.1 Replay 的定位

当前只实现 Command Re-execution：同一批 Command 在全新引擎中重新执行，再验证结果是否完全一致。

它没有实现 `apply_event()`，也没有从 EngineEvent 恢复状态。

### 13.2 使用方式

```cpp
#include "replay.hpp"

std::vector<Command> commands{
    NewOrderCommand(CommandSequence(1), OrderId(1), Side::SELL,
                    from_double(10.00), Quantity(100)),
    NewOrderCommand(CommandSequence(2), OrderId(2), Side::BUY,
                    from_double(10.00), Quantity(40)),
    CancelOrderCommand(CommandSequence(3), OrderId(1))
};

OrderBook expected(64);
for (const Command& command : commands) {
    (void)expected.process(command);
}

CommandReplayVerification result =
    ReplayEngine::verify_commands(commands, expected);

if (!result.success()) {
    // first_mismatched_event、事件数量、hash 和 invariant_error()
    // 可以帮助定位失败层次。
}
```

### 13.3 验证顺序

Replay 接口自身执行：

1. `EngineEvent` 数量和每个 variant 全字段比较；
2. 完整 `OrderBookState` 比较；
3. 原始和重放引擎分别 `check_invariants()`；
4. `state_hash()` 辅助比较。

`success()` 要求四层全部通过。

### 13.4 为什么不能只比较 BBO 或 hash

BBO 相同不能证明深层价格档和 FIFO 相同。hash 理论上可能碰撞，也可能因为两边共享同一错误而相同。逐字段状态能提供最直观证据，invariant 检查内部结构，hash 适合快速摘要；四者职责不同。

### 13.5 Sequence gate 拒绝在 Replay 中怎样处理

Replay 会按原 Command 列表逐条调用 `process()`。重复或倒退 sequence 在两边都返回准入拒绝，但不会产生 EngineEvent，也不会污染事件序列。后续合法命令仍按最后真正消费的 sequence 判断。

## 14. CSV 事件诊断

```cpp
ReplayEngine::save_log(book.engine_events(), "events.csv");
std::vector<EngineEvent> loaded = ReplayEngine::load_log("events.csv");
```

它会保存和严格解析当前四种 EngineEvent，可用于：

- 人工阅读一次执行结果；
- 检查事件序列化字段；
- 做 CSV 往返测试；
- 调试测试失败。

它不能用于：

- 从 Event 猜回 Command；
- 重建订单簿；
- 崩溃安全恢复；
- 替代 CommandJournal 或 ExecutionJournal。

文件目前没有格式版本、校验和、配置指纹和原子落盘协议。

## 15. 轻量内存 Snapshot

### 15.1 Snapshot 保存什么

```cpp
struct OrderBookSnapshot {
    uint32_t snapshot_version;
    CommandSequence last_applied_command_sequence;
    InstrumentConfig instrument_config;
    PriceLadderConfig price_ladder_config;
    std::vector<SnapshotOrder> active_orders;
};
```

每笔 `SnapshotOrder` 保存：

- OrderId；
- Side；
- Price；
- original quantity；
- remaining quantity；
- PrioritySequence。

不保存内部指针、订单池槽地址、链表指针、map 节点或缓存指针。

### 15.2 创建和恢复

```cpp
#include "snapshot_recovery.hpp"

OrderBookSnapshot snapshot = book.create_snapshot();

SnapshotRestoreResult restored =
    SnapshotRecovery::restore(snapshot, book.capacity());

if (!restored.success()) {
    std::cerr << to_string(restored.error) << '\n';
    return 1;
}

OrderBook& new_book = *restored.book;
```

恢复返回一个全新的 `OrderBook`，不会修改原引擎。

### 15.3 恢复前校验

当前会检查：

- `snapshot_version == 1`；
- InstrumentConfig 和 PriceLadderConfig 合法；
- 活跃订单数不超过恢复容量；
- OrderId 非零且不重复；
- Side 合法；
- 价格、tick、数量、lot 合法；
- 剩余量大于 0 且不超过原始量；
- PrioritySequence 非零、不重复且不晚于最后 CommandSequence；
- 同档数量汇总不溢出；
- 快照没有 crossed book。

通过后按方向、价格和 PrioritySequence 排序，再重建订单池、ID 索引、价格层、FIFO、价格梯和 best bid/ask，最后恢复 sequence 并执行 `check_invariants()`。

### 15.4 原子失败

失败结果包含明确 `SnapshotRestoreError` 和空 `book`。因为恢复在新对象中完成，调用者不会拿到半恢复状态，原来的运行引擎也不受影响。

### 15.5 恢复后继续执行

后续 CommandSequence 必须严格大于快照中的最后序列。恢复引擎的历史事件容器是空的，因此只能把它的后续事件与未中断引擎同一位置之后的事件后缀比较。

### 15.6 Snapshot 不是什么

- 不写磁盘；
- 不压缩；
- 不含 checksum；
- 不是进程崩溃恢复；
- 不是复杂版本兼容系统；
- 不保存历史 EngineEvent。

## 16. 状态审计工具

### 16.1 capture_state()

适合做可读、逐字段的完整订单簿比较，是 Replay 和 Snapshot 测试的主要正确性证据。

### 16.2 check_invariants()

检查链表、价格档汇总、索引、对象池、层池、价格梯、缓存、FIFO 和非交叉账本。它是 O(活跃订单数) 的重操作，适合测试、恢复后和低频健康检查。

```cpp
if (!book.check_invariants()) {
    throw std::runtime_error("order book invariant broken");
}
```

### 16.3 state_hash()

按稳定顺序混合：

- last applied command sequence；
- 买卖侧和价格档；
- 每笔活跃订单 ID；
- PrioritySequence；
- 剩余数量。

它适合快速发现差异，但不是密码学证明，也不能代替完整状态和 invariant。

## 22. 性能数据和正确口径

性能阶段原始结果保存在 `benchmarks/results/`。对应代码提交 `e4d59e2`，不是最终架构 HEAD 的重新测量。

环境：Intel Core i7-14650HX、Windows、MSVC 19.44、x64 Release、Balanced、线程未绑核、关闭事件。聚合方式：5 个新进程，每进程 7 次，取进程中位数后再取中位数。

| 场景 | 优化前 | 优化后 |
|---|---:|---:|
| 同价已有层 | 44.559 ns/order | 26.663 ns/order |
| 多个已有层 | 43.876 ns/order | 27.104 ns/order |
| 新价格层 | 79.730 ns/order | 73.090 ns/order |
| 立即成交 | 43.838 ns/order | 24.988 ns/order |
| 扫四档 | 200.090 ns/order | 186.440 ns/order |

这组数据可以说明数据结构优化对特定路径有效，不能说明：

- 所有订单都在 30 ns 内完成；
- 开启事件后仍是相同数字；
- 最终架构 HEAD 已重新得到相同结果；
- 网络到网络的端到端延迟是 30 ns；
- Windows 尾延迟已达到生产交易所水平。

最准确的结论是：三个受限、预热、关闭事件的批量微基准达到约 25–27 ns；新价格档和多档成交仍明显高于 30 ns。

## 24. 常见问题

### Q1：项目稳定达到 30 ns 了吗？

不能这样说。性能提交的三个窄微基准约 25–27 ns，但新价格层约 73 ns、扫四档约 186 ns，而且最终架构提交尚未重跑同一矩阵。30 ns 是特定路径结果，不是统一承诺。

### Q2：为什么 sequence gate 拒绝不生成 OrderRejectedEvent？

因为它表示输入未被接纳，而 `OrderRejectedEvent` 表示已经消费的命令得到业务拒绝结果。这样未来若引入 Journal，输入和执行结果边界更一致。

### Q3：业务拒绝为什么还要推进 last sequence？

因为这条命令已经被引擎按顺序消费。如果不推进，同一序列随后可被重复使用，会破坏确定性输入历史。

### Q4：PrioritySequence 为什么不用时间戳？

FIFO 只需要稳定的逻辑先后。真实时间有发送、接收、网关和交易所多种含义，把它直接用于核心顺序会让 Replay 和恢复语义变复杂。

### Q5：CSV 为什么不能恢复订单簿？

当前 CSV 保存的是执行结果 Event，不是权威输入 Command，也没有版本、校验和和崩溃写入协议。它只用于诊断往返。

### Q6：Snapshot 能不能保存到文件后重启恢复？

当前没有文件格式和磁盘安全协议。数据结构本身不含指针，理论上为以后序列化提供了基础，但现在不能宣称支持重启恢复。

### Q7：为什么还保留 `std::map`？

它提供清楚、可靠、任意合法价格的完整排序。PriceLadder 已加速常见已知价，但替换最优价目录需要真实价格分布、更多差分测试和内存权衡，不能只为一个数字贸然删除。

### Q8：它能直接做策略回测吗？

它可以作为撮合核心。完整回测还要在外层增加历史数据适配、策略调度、费用、滑点、持仓、现金、交易时段和多品种管理。

## 25. 总结介绍

> 我基于一个开源 C++ 撮合引擎原型做了工程化改造。先修复 Visual Studio 构建、交易规则和容量失败，再用固定开放寻址索引替换热路径 unordered_map，让订单直连价格层，并把价格层池接入真实撮合路径。性能阶段用固定场景和多进程中位数验证，三个关闭事件的窄路径做到约 25–27 ns，但我没有把它宣传成端到端 30 ns。随后我停止微优化，把输入 Command 和输出 EngineEvent 分开，引入 CommandSequence、EventIndex 和 PrioritySequence，Replay 改为在全新引擎重执行 Command，并比较全部 Event 字段、完整订单簿、invariant 和 hash；又增加了不保存指针的内存 Snapshot，可以原子地恢复一个新引擎。最终 Release 和 MSVC ASan 都是 4/4 CTest 通过。

这段介绍的重点是能够继续回答：为什么这样设计、怎样证明正确、什么还没有做，以及性能数据属于哪一个版本和场景。
