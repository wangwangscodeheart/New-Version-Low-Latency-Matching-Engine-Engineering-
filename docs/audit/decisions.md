# M0：首批架构决策记录（ADR）

日期2026-11-11；依据基线`c690dfd`。这里明确选择与后续门禁，不把方案伪装成实现。M0不改撮合核心；后续影响API/恢复语义的补丁应引用相应ADR并记录证据。

## ADR-001：进程内应用与持久化/发布完成分离

状态：M1第三批已实现标准CommandJournal进程内预留/整组接受接口；2026-11-19 M2进一步实现可选的提交后公开入队及独立下游应用，见[M2闭环](../M2_PUBLIC_FEED.md)。磁盘durable、真实网络与崩溃续接仍待后续，不把该ADR整体标为完成。见[第三批记录](../M1_BATCH_03.md)。

背景：`OrderBook::process`先改状态再交付；Journal在ORDER回调中失败不阻止当前命令。`APPLIED`只证明核心应用，不证明日志完整、已持久化或下游可信。

决定：保留现有核心状态语义，显式区分“进程已应用 / 完整命令记录已接受 / durable / 公开发布 / 消费者已应用”。不以timestamp、accepted_count或written_count替代这些状态，不宣称Exactly-Once。先在应用层定义完整命令边界，再讨论崩溃提交点。

代价与失败：增加状态和水位管理；不可把已应用但缺输出的命令重新当普通新命令撮合。验收必须故障注入，比较权威状态和完整事件。回滚时恢复旧接口同时恢复旧的orderly-stop限制，不能继续保留新承诺。

## ADR-002：可靠输出按完整命令处理，不能只丢弃后缀

状态：OrderBook有界待发已在第二批实现，标准Journal整命令接受已在第三批实现；磁盘持久化与全部发布契约未完成，参见各批次记录。

选择：优先使用有上限的命令事件批次及容量准入/预留，可靠订阅者接受完整批次后才放行下一条命令；若运行期失败而命令已应用，保持明确的未完成批次/不可用状态，并停止后续准入，不能释放后缀后继续声称下游可信。无损补发是否支持以及谁持有批次，必须由测试验证，不只新增bool。

拒绝的替代：对撮合热路径直接同步写磁盘；静默丢公开行情；把普通日志丢弃策略照搬到恢复Journal；立即引入复杂无锁框架。

性能影响：预留内存和背压会降低容量极限下吞吐，但行为可解释。异步Audit/诊断日志可单独允许丢弃，必须计数并标记不完整。事件容量要覆盖拒绝/多档成交/撤销剩余，不能只按固定“每命令一个事件”估算。

验收：固定容量、队列满、订阅者失败、恢复重试、最大跨档成交；可确认失败不产生未标记的永久不一致。R03/R05是修复前证据，不是验收目标。此ADR不保证运行期分配异常已事务化。

## ADR-003：公开行情采用明确的L3-like可见订单语义

状态：M2方案；当前没有Builder/Publisher。

决定：最小增量先连接现有逐订单Add/Cancel/Trade消费模型；公开字段不直接复用所有私有EngineEvent，不把aggressive_order_id等账户侧信息默认公开。精确定义Add、部分扣减、完全移除、IOC/Post-Only与sequence。公开簿可比较可见订单/聚合深度，不宣称现有MarketDataBook重建FIFO。

理由：已有decoder与本地簿可复用，闭环需要的新增范围小于另建L2协议。并非宣称Nasdaq ITCH兼容；真实协议适配独立验收。

验收：权威可见投影→独立编码/解码→本地簿；每命令对照、丢包/重复/乱序→STALE。私有执行回报与公开流分离。回滚时保留现有独立Feed测试，不影响V1核心。

## ADR-004：快照必须有版本、唯一generation与完整命令截点

状态：generation不覆盖/非复用已在[M1第八批](../M1_BATCH_08.md)增量实现；真实durable截点、崩溃验收及Feed拼接仍待M3，不将整个ADR标为完成。

决定：保留同代Book文件先写、manifest最后替换机制；generation不可覆盖仍被有效manifest引用的文件。定义快照截点所属序列域，与Journal完整命令提交边界关联。消费者从可信快照基准开始，只应用后续连续增量；恢复中不暴露VALID。

现有差距：本地Feed只有内存checkpoint，首序号任意接受；多簿后缀筛选由测试调用者手工做，无统一服务编排。不能用snapshot_sequence一个整数掩盖不同序列域。

验收：相同generation重复请求、manifest替换前崩溃、损坏文件、增量重复/缺口、恢复中再次失败。故障时上一份有效快照可读；孤儿文件清理不进入撮合热路径。

## ADR-005：单簿单写者是默认，不先上线程池分片

状态：延续并明确当前设计。

决定：保持OrderBook和当前MarketManager/Dispatcher调用线程有序。未来多连接在Sequencer前汇入，明确每簿序列域；跨symbol全序或跨分区事务不作现有能力承诺。控制面快照与订阅停止必须由所有者安排静止点。

理由：现有池内指针、索引prepare/commit、FIFO依赖独占写；直接加锁/CAS/线程池不能替代顺序和提交契约。是否分片到M4同输入性能与业务不变量验证后再定。

验收：文档和API说明一致；并发能力只在真实测试范围内声明。当前bounded queue的多线程同步不意味着整个引擎支持并发submit。

## ADR-006：现有CSV Journal只承诺正常关闭；durable prefix另行实施

状态：当前保证已确认；新持久化策略待M3评估并实现。

当前决定：仅在worker无错误、有序drain/flush并验证完整Journal后谈正常关闭恢复；written不是durable watermark。快照虽然调用平台刷新API，也不把整个系统升级为断电一致性WAL。

后续首选评估：版本/长度/校验/完整命令commit frame，加显式batch sync策略与durable_sequence；不在本轮杜撰fsync频率或承诺零丢失。恢复只接受校验通过且命令完整的持久化前缀，区分尾部截断与中间损坏。

验收：强杀/截断/翻位/磁盘满/刷新失败/重启续写，给出已确认恢复水位、未确认命令的处置和原始日志。同步策略的延迟/吞吐单独测量，不能沿用当前不含drain的benchmark作为durable latency。
